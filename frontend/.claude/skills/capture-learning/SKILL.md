# Capture Learning — 다음 작업을 쉽게 만든다

이번 작업의 교훈을 검색 가능한 형태로 남기고, 하네스 자체를 개선한다.

## 실행 모드: 서브 에이전트 1명

`learning-compounder` 한 명이 문서화를 담당한다. 단발성 문서 작성이고 교차 검증할 상대가 없으므로 팀을 만들지 않는다.

## 판단 먼저: 남길 것이 있는가

문서를 만들기 전에 남길 가치를 판단한다. **모든 작업이 학습을 만들지 않는다.** 억지 문서는 검색 결과를 오염시켜 진짜 학습을 묻는다.

| 남긴다 | 남기지 않는다 |
|--------|-------------|
| 원인 파악에 시간이 걸린 결함 | 오타·단순 실수 |
| 이 프로젝트에서만 통하는 제약·규약 | 프레임워크 공식 문서에 있는 내용 |
| 두 번째로 겪은 유형의 문제 | 재발 가능성 낮은 일회성 |
| 어떤 접근을 택하고 다른 것을 버린 이유 | 자명한 선택 |
| Next.js 16이 학습 데이터와 달랐던 지점 | 일반적인 React·TypeScript 지식 |
| 리뷰가 "반복 유형"으로 표시한 발견 | 리뷰가 관찰로만 남긴 사소한 것 |

남길 것이 없으면 문서를 만들지 않고 "학습 없음 — <이유>"를 보고한다. 이것은 실패가 아니라 정상 결과다.

## 워크플로우

### Phase 0: 입력 수집

가능한 것을 모은다. 없는 것은 없는 대로 진행한다.

| 입력 | 경로 | 용도 |
|------|------|------|
| 계획 | `docs/plans/<...>-plan.md` | 무엇을 하려 했는가 |
| 구현 요약 | `_workspace/<plan-slug>/02_work_summary.md` | 계획과 달라진 점, 차단 |
| 리뷰 보고 | `_workspace/<plan-slug>/03_review_*.md` | 발견된 결함, "반복 유형" 표시 |
| 대화 맥락 | 현재 세션 | 실제로 막혔던 지점 — 파일에 남지 않는 가장 중요한 입력 |

계획·요약이 없는 단독 호출(사용자가 문제를 고친 직후 "기록해줘")도 정상이다. 대화 맥락만으로 진행한다.

### Phase 1: 중복 확인

`docs/solutions/`를 검색한다. 없으면 이 단계를 건너뛴다 (첫 학습).

```bash
ls docs/solutions/ 2>/dev/null || echo "없음"
grep -rl "<핵심 키워드>" docs/solutions/ 2>/dev/null
```

| 겹침 | 조치 |
|------|------|
| 같은 문제·원인·해법 | **기존 문서를 갱신한다.** `updated:` 추가, 새 예시 반영. 새 파일 금지 |
| 같은 영역, 다른 원인/해법 | 새 문서 + 기존 문서 상호 링크 |
| 무관 | 새 문서 |

같은 문제를 설명하는 두 문서는 반드시 갈라지고, 나중에 어느 쪽이 맞는지 아무도 모른다.

### Phase 2: 문서화

`learning-compounder`를 호출한다 (`model: "opus"`).

프롬프트에 포함할 것:
- Phase 0에서 모은 입력 경로들
- **이번 세션에서 실제로 막혔던 지점** (대화에서 직접 추출해 전달 — 에이전트는 이 세션의 대화를 볼 수 없다)
- Phase 1의 중복 판정 결과 (갱신 대상 파일 경로 또는 "중복 없음")
- 카테고리 후보

한 실행에서 학습 후보가 여러 개면 **가장 재사용 가치가 큰 하나만** 문서화하고 나머지는 추가 후보로 보고한다. 여러 교훈을 한 문서에 섞으면 검색해서 찾은 사람이 자기와 관련 없는 절반을 읽어야 한다.

### 카테고리

| 카테고리 | 대상 |
|----------|------|
| `boundary-issues/` | API 계약·타입·라우트·환경변수 경계면 결함 |
| `nextjs-16/` | Next.js 16이 학습 데이터·이전 버전과 달랐던 지점 |
| `testing/` | vitest 제약, 테스트 가능하게 만드는 구조 |
| `build-errors/` | 빌드·타입 검사 실패와 원인 |
| `conventions/` | 이 프로젝트에서 합의된 방식 |
| `patterns/` | 재사용 가능한 구현 패턴과 선택 이유 |

### Phase 3: 하네스 개선 반영

학습 문서와 별개로, 이번 실행에서 **하네스 자체가 놓친 것**을 식별한다. 이것이 하네스를 진화시키는 유일한 경로다.

| 신호 | 수정 대상 |
|------|----------|
| 계획에 필요한 정보가 빠져 구현자가 되물었다 | `.claude/agents/plan-architect.md` 또는 계획 템플릿 |
| 리뷰가 놓친 결함이 나중에 발견됐다 | `.claude/agents/boundary-reviewer.md` 또는 `references/boundary-checklist.md` |
| 구현자가 같은 실수를 반복했다 | `.claude/agents/unit-implementer.md` |
| 스킬이 트리거되지 않았다 | 해당 SKILL.md의 `description` |
| 위험도 판정이 틀렸다 (Tier 1인데 경계면 버그) | `.claude/skills/lite-review/SKILL.md`의 판정 신호 표 |

**같은 유형의 문제가 2회 이상 발생했으면** 그것을 명시한다. 반복은 하네스 수정이 필요하다는 신호다.

수정을 제안하되 사용자 승인 없이 하네스 파일을 고치지 않는다. 하네스 변경은 이후 모든 작업에 영향을 주므로 사용자가 판단해야 한다.

### Phase 4: 변경 이력 기록

하네스 수정이 승인되면 `frontend/CLAUDE.md`의 **변경 이력** 표에 한 줄을 추가한다:

```markdown
| 2026-07-29 | 경계면 체크리스트에 core 빌드 확인 항목 추가 | skills/lite-review/references/ | core 소스만 바꾸고 빌드 안 해 리뷰가 옛 코드를 봤음 |
```

이력이 없으면 하네스가 어느 방향으로 진화했는지 추적할 수 없고, 같은 수정을 되돌리는 퇴행이 발생한다.

### Phase 5: 보고

```
학습 정리 완료

**문서:** docs/solutions/<category>/<slug>.md (생성 | 갱신) — <제목>
또는 **문서:** 없음 — <이유>

**추가 학습 후보:** <있으면 나열, 없으면 "없음">

**하네스 개선 제안:** N건
1. `<대상 파일>` — <문제> → <제안>

**반복 신호:** <2회 이상 발생한 유형. 없으면 "없음">

하네스 개선을 적용할까요?
```

```

    ↓

    ↓
[learning-compounder]
    ├──→ docs/solutions/<category>/<slug>.md  (생성 또는 갱신)
    └──→ 하네스 개선 제안
              ↓
        사용자 승인 게이트
              ↓
    하네스 파일 수정 + CLAUDE.md 변경 이력
```

## 에러 핸들링

| 상황 | 전략 |
|------|------|
| `docs/solutions/`가 없음 | 만든다. 첫 학습이 디렉토리를 만드는 것이 정상 흐름이다 |
| 작업이 실패로 끝남 (구현 미완·차단) | 그래도 학습은 있다 — "무엇이 막았는가"가 가장 가치 있을 수 있다. 단, 미해결 문제의 `해결` 섹션을 추측으로 채우지 않는다. 미해결임을 명시한다 |
| 학습 후보가 여러 개 | 가장 가치 큰 하나만 문서화. 나머지는 추가 후보로 보고해 사용자가 별도 실행을 결정하게 한다 |
| 근거 파일이 이번 변경으로 삭제됨 | 존재하지 않는 경로를 근거로 인용하지 않는다. 삭제 사실을 문서에 명시한다 |
| 하네스 개선 제안이 5건 초과 | 우선순위를 정해 상위 2~3건만 제안한다. 하네스를 한 번에 크게 바꾸면 어느 변경이 효과를 냈는지 알 수 없다 |
| 사용자가 하네스 수정을 거절 | 제안을 학습 문서의 `## 관련`에 기록해 남긴다. 다음에 같은 문제가 반복되면 근거가 된다 |

## 테스트 시나리오

### 정상 흐름
1. 구현·리뷰 완료. 리뷰가 "백엔드 DTO 필드명 불일치 — 타입 캐스팅이 컴파일러 검증을 우회" 차단을 잡았음
2. Phase 1: `docs/solutions/` 미존재 → 첫 학습
3. Phase 2: `learning-compounder`가 `docs/solutions/boundary-issues/api-response-cast-bypasses-typecheck.md` 작성. 근거로 `src/lib/api/itinerary.ts:68` 인용
4. Phase 3: 개선 제안 — "boundary-checklist에 `as T` 캐스팅 지점 목록화 항목 추가"
5. Phase 4: 사용자 승인 → 체크리스트 수정 + CLAUDE.md 이력 1줄
6. 예상 결과: 학습 문서 1개 + 하네스 파일 1개 수정 + 이력 1줄

### 학습 없음 흐름
1. 작업이 Tailwind 클래스 조정 2파일, 리뷰 차단 0건, 막힌 지점 없음
2. Phase 0~1: 입력 수집, 중복 확인
3. 판단: 남길 것이 없다 (프레임워크 지식·일회성 스타일 변경)
4. 보고: "문서: 없음 — 재사용 가능한 교훈 없음(스타일 조정, 막힌 지점 없음). 하네스 개선 제안: 없음"
5. 예상 결과: 파일 생성 0개. 이것이 올바른 결과다
