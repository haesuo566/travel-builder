# Unit Work — 계획 유닛을 구현하고 검증한다

계획의 구현 유닛을 순서대로 실행한다. 유닛 하나 = 커밋 하나 = 리뷰 단위.

## 실행 모드: 서브 에이전트

**이 환경에는 `TeamCreate`가 없다.** 에이전트 팀 모드(팀원 간 자체 조율, 공유 작업 목록 claim)는 성립하지 않는다. 사용 가능한 조율 수단은 이것뿐이다:

| 수단 | 용도 |
|------|------|
| `Agent`(한 메시지에 여러 호출) | 병렬 실행 |
| `Agent`의 `name` 파라미터 | 실행 중 에이전트를 주소 지정 가능하게 만든다 |
| `SendMessage({to: name})` | 실행 중인 구현자에게 리더가 정보 전달 |
| 반환값 | 구현자 결과 수집 |
| 파일 (`_workspace/`) | 대용량 산출물, 감사 추적 |
| `TaskCreate`/`TaskUpdate` | 진행 상황 노출 |

**경계면 통지는 리더를 경유한다.** 구현자 A가 공유 타입을 바꾸면 리더에게 보고하고, 리더가 실행 중인 구현자 B에게 `SendMessage`로 전달한다. 구현자끼리 직접 조율하는 설계를 쓰지 않는다 — 이 환경에서 검증되지 않았고, 서로의 이름을 알 보장이 없다.

### 병렬 판정

| 상황 | 실행 |
|------|------|
| 유닛의 `파일` 목록이 겹치지 않음 + 공유 자원도 없음 | **병렬** (한 메시지에 여러 `Agent` 호출, 각 `name: "impl-u<n>"`, `run_in_background: true`) |
| 파일이 겹치거나 아래 공유 자원을 함께 건드림 | **순차** |
| 의존 관계가 있음 (`의존: U1`) | 선행 유닛 완료 후 |

공유 자원 — 파일 목록이 달라도 순차로 돌려야 하는 것:
- `src/lib/types.ts` 등 공유 타입
- `src/lib/api/*.ts` 등 API 계약
- `.env*`, `next.config.ts`, `package.json`, `vitest.config.ts`
- 같은 라우트 세그먼트
- 생성 산출물·lockfile

공유 작업 디렉토리에서 병렬 실행하면 같은 파일에 대해 **마지막 쓰기만 남는다.** 겹침 판정을 건너뛰면 한 구현자의 작업이 조용히 사라진다.

동시 실행은 3명을 넘기지 않는다. 그 이상은 통합·충돌 비용이 병렬 이득을 넘는다.

## 워크플로우

### Phase 0: 컨텍스트 확인

1. 대상 계획을 특정한다:
   - 사용자가 경로를 줬으면 그것
   - 없으면 `docs/plans/`에서 가장 최근 파일. 후보가 둘 이상이면 사용자에게 확인
2. 계획을 읽는다. 긴 계획은 `## 문제와 범위`, `## 경계면 영향`, `## 구현 유닛` 제목 목록을 먼저 보고, 실행할 유닛 섹션만 전문을 읽는다
3. **이미 구현된 유닛을 판별한다** — 계획에 진행 상태를 기록하지 않는다. 대신:
   - `git log --oneline -20`으로 이 계획 관련 커밋 확인
   - 각 유닛의 `파일`이 실재하고 `검증` 기준이 이미 충족되는지 확인
   - 충족된 유닛은 건너뛴다. 다시 구현하지 않는다

4. **미커밋 변경을 hunk 단위로 분류한다** (재개 시 필수)

   `git status`가 더러우면 그 변경을 그대로 검증·커밋해서도, 그대로 원복해서도 안 된다. 두 형태가 겉모습이 같기 때문이다:

   ```bash
   git status --short
   git diff          # 파일 단위가 아니라 hunk 단위로 계획과 대조한다
   ```

   | 분류 | 판단 기준 | 조치 |
   |------|----------|------|
   | **진행분** | 계획의 어느 유닛 블록과 일치한다 | 검증(`tsc`·`test`·`lint`)만 하고 그 유닛으로 커밋한다. **검증 없이 커밋하지 않는다** — 중단된 세션이 검증까지 갔다는 증거가 없다 |
   | **근거 없는 변경** | 계획에도 HEAD에도 근거가 없다 | **원복하고 기록한다.** 원인을 못 찾아도 "원인 불명이라 유지"는 선택지가 아니다 |

   근거 없는 변경을 남기면 이후 커밋에 섞여 들어가 어느 커밋의 의도였는지 영구히 알 수 없게 된다. 실제로 이 리포에서 핸들러 호출 두 개가 뒤바뀐 stray 변경이 발견됐고, 그 시점에는 **테스트가 초록불로 통과했다.** 테스트 통과는 이 분류를 대신하지 못한다.

   분류 결과를 `_workspace/<plan-slug>/02_work_summary.md`에 먼저 쓴 다음 재개 지점을 정한다.

5. 실행 모드를 결정한다:

| 상황 | 모드 |
|------|------|
| 구현된 유닛 없음, 트리 깨끗 | 초기 실행 — 전 유닛 |
| 일부 구현됨 | 이어서 — 미구현 유닛만 |
| 사용자가 특정 U-ID 지정 | 부분 재실행 — 그 유닛만 |
| 리뷰 피드백 반영 요청 | 수정 실행 — 지적된 파일만, 지적 범위 안에서 |

### Phase 1: 준비

1. 브랜치를 확인한다:
   ```bash
   git branch --show-current
   ```
   - 기본 브랜치(`main`)면 계획 제목에서 이름을 만들어 생성한다: `feat/<slug>`, `fix/<slug>`
   - 이미 의미 있는 이름의 피처 브랜치면 그대로 쓴다
   - `main`에 직접 커밋하지 않는다
2. `.claude/_workspace/<plan-slug>/`가 없으면 만든다
3. 작업 목록을 만든다 (`TaskCreate`). 제목에 U-ID를 접두사로 붙인다: `U1: <유닛 제목>`. 계획의 `의존`을 작업 의존성으로 반영한다

### Phase 2: 구현

유닛을 의존 순서대로, 병렬 판정에 따라 `unit-implementer`에게 위임한다 (`subagent_type: "unit-implementer"`, `model: "opus"`, `name: "impl-u<n>"`).

각 프롬프트에 포함할 것:
- 계획 파일 절대 경로 + 배정 U-ID
- **그 유닛 섹션 전문** (목표/파일/따를 패턴/테스트 시나리오/검증/의존)
- 계획의 `## 문제와 범위`, `## 경계면 영향` 섹션 전문
- "커밋하지 말 것 — 커밋은 리더가 승인 후 수행한다"
- 병렬 실행 중이면: 동시 실행 중인 유닛 번호와 그 파일 범위 (침범 방지)

계획 전문을 읽으라는 지시를 프롬프트로 주지 않는다. 필요한 조각을 직접 넣는다 — 구현자가 계획 전체를 읽으면 컨텍스트 대부분이 자기 유닛과 무관한 내용으로 채워진다.

**경계면 통지 (리더의 책임)**

구현자가 공유 타입·API 계약·라우트·환경변수를 바꿨다고 보고하면, 리더는 **실행 중인** 다른 구현자에게 즉시 전달한다:

```
SendMessage({to: "impl-u3", summary: "U2가 types.ts 변경", message: "..."})
```

늦게 전달하면 상대는 이미 옛 계약으로 구현을 끝낸 상태다. 병렬 배치를 시작하기 전에 각 구현자가 어느 경계면을 건드릴 예정인지 계획에서 미리 확인해, 통지가 필요한 조합을 파악해 둔다.

**유닛 하나가 끝날 때마다:**
1. `git diff`로 변경이 유닛의 `파일` 범위 안인지 확인한다. 넘었으면 이유를 확인하고 사용자에게 보고
2. 유닛의 `검증` 명령을 리더가 직접 실행한다 (구현자 보고를 신뢰하되 확인)
3. 구현자 보고의 검증 증거를 `02_work_summary.md`에 누적 기록
4. Phase 3 커밋 게이트를 거친다
5. 다음 유닛을 위임한다. **깨진 트리 위에서 다음 유닛을 시작하지 않는다**

**병렬 배치가 끝나면 리더가 통합한다:**
1. 모든 구현자 완료를 대기
2. **보고된 파일 목록이 아니라 실제 트리를 본다** — `git status`, `git diff`. 구현자는 계획이 예상하지 못한 파일을 만들거나 고친다
3. 실제 충돌(둘 이상이 같은 파일 수정)을 확인한다. 공유 디렉토리에서는 마지막 쓰기만 남으므로, 충돌하지 않은 유닛을 먼저 커밋한 뒤 충돌한 유닛을 순차로 다시 실행한다
4. 유닛별로 검증 실행 → 커밋 게이트

### Phase 3: 커밋 게이트 (유닛별 승인)

유닛 하나가 검증을 통과하면 커밋을 제안한다. **승인 없이 커밋하지 않는다.**

```
U<n> 완료: <유닛 제목>

**변경 파일**
- `경로` — <무엇>

**검증**
- `<명령>` → <결과>
- 테스트: 추가/수정 `경로` (또는 없음 + 이유)

**커밋 메시지 제안**
<type>(<scope>): <한 줄 요약>

커밋할까요?
```

승인되면:
```bash
git add <이 유닛의 파일만>    # git add . 금지 — 유닛 경계가 커밋 경계다
git commit -m "<승인된 메시지>"
```

커밋 메시지는 이 리포의 관례를 따른다: 한국어 본문, `<type>(<scope>): <동작>` 형식, 명령형 종결(`~한다`). `git log --oneline -10`으로 실제 스타일을 확인한다.

사용자가 "이후 커밋은 묻지 말고 진행"이라고 하면 그 세션 동안 게이트를 생략한다. 기본값은 매 유닛 확인이다.

### Phase 4: 완료 보고

1. `_workspace/<plan-slug>/02_work_summary.md`를 완성한다:
   ```markdown
   # 구현 요약: <계획 제목>

   ## 재개 시점 실측 (재개 실행일 때)
   - 미커밋 변경 분류: 진행분 <목록> / 근거 없는 변경 <목록, 원복함>

   ## 유닛 결과
   | U-ID | 상태 | 커밋 | 검증 |
   |------|------|------|------|

   ## 경계면 변경
   - <구현 중 실제로 바뀐 공유 타입/계약/라우트. 리뷰의 위험도 판정 입력이 된다>

   ## 계획과 달라진 점
   - <계획이 예상하지 못해 다르게 한 것>

   ## 미완료·차단
   - <끝내지 못한 유닛과 이유>
   ```
2. 사용자에게 요약을 보고하고 리뷰 진행 여부를 확인한다 (dev-flow가 호출한 경우 리더에게 반환)

## 데이터 흐름

```
docs/plans/...-plan.md
    ↓ (유닛 패킷)
[unit-implementer] × N  (병렬: 한 메시지에 여러 Agent 호출, name 지정)
    ↑ 경계면 변경 보고 ──→ [리더] ──→ SendMessage로 다른 구현자에 전달
    ↓ 코드 변경 + 검증 증거
[리더] 실제 트리 확인 → 검증 재실행 → 커밋 게이트 → 커밋
    ↓
_workspace/<plan-slug>/02_work_summary.md
```

## 에러 핸들링

| 상황 | 전략 |
|------|------|
| 구현자가 차단 보고 | 차단 사유를 읽고 판단한다. 계획 전제가 틀렸으면 사용자에게 계획 수정을 제안한다. 우회 구현을 지시하지 않는다 |
| 검증 명령 실패 | 기존 실패인지 확인 (`git stash` 후 재실행). 이번 변경 때문이면 같은 구현자에게 수정 요청 (1회). 재실패 시 사용자에게 보고 |
| 구현자가 유닛 범위를 넘어 수정 | `git diff`로 범위 외 변경을 특정한다. 불필요하면 되돌린다. 필요했으면 커밋 메시지에 포함하고 계획의 결함으로 기록 |
| 병렬 구현자 간 같은 파일 충돌 | 충돌하지 않은 유닛을 먼저 커밋한 뒤, 충돌한 유닛을 순차로 다시 실행한다 (각자 상대의 커밋된 결과 위에서) |
| 구현자 1명 실패/무응답 | 1회 재시도. 재실패 시 그 유닛을 순차로 다시 실행한다 |
| 유닛 절반 이상 차단 | 구현을 계속하지 않는다. 계획 전제 문제 신호다. 사용자에게 보고하고 계획 재작성 여부를 확인한다 |

## 테스트 시나리오

### 정상 흐름
1. 계획 유닛 3개. U1(`src/lib/toast.ts` 신규) → U3(`ChatPanel.tsx` 연결), U2(`src/components/ui/Toast.tsx` 신규) 독립
2. Phase 0: 커밋 이력 확인 → 구현된 유닛 없음, 트리 깨끗
3. Phase 1: `main`이므로 `feat/chat-error-toast` 생성, 작업 3개 등록
4. Phase 2: U1·U2 파일 겹침 없음 → 한 메시지에 `Agent` 2개 호출 (`name: "impl-u1"`, `"impl-u2"`). U3은 U1 완료 후
5. `impl-u1`이 `src/lib/types.ts`에 `ToastKind` 추가를 보고 → 리더가 `SendMessage({to: "impl-u2"})`로 전달
6. 배치 완료 → `git status`로 실제 변경 확인 → 충돌 없음 → 유닛별 검증 → 커밋 승인 3회
7. Phase 4: `02_work_summary.md`에 경계면 변경(`types.ts`) 기록
8. 예상 결과: 3커밋 + 요약 파일. 리뷰 Tier 2 상승 입력이 준비됨

### 재개 흐름
1. 사용자: "어제 하던 작업 이어서"
2. Phase 0: U1 커밋 존재. `git status`가 더러움 — `src/lib/toast.ts` 수정 + `src/lib/api/itinerary.ts` 수정
3. hunk 대조: `toast.ts` 변경은 U2 블록과 일치 → **진행분**. `itinerary.ts` 변경은 계획 어느 유닛에도 없음 → **근거 없는 변경**
4. `itinerary.ts` 원복 + `02_work_summary.md`에 기록. `toast.ts`는 검증 후 U2로 커밋
5. U3부터 재개
6. 예상 결과: stray 변경이 커밋에 섞이지 않는다
