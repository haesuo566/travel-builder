# Lite Review — 위험도에 맞춘 최소 비용 리뷰

변경 diff만 본다. 위험도로 리뷰어 수를 정한다. 라운드는 1회다.

## 실행 모드: 서브 에이전트 (1~2명 병렬)

리뷰어를 격리해서 돌린다. 리뷰의 가치는 구현 맥락에 물들지 않은 독립 판단이므로, 구현자와의 실시간 통신이 오히려 판단을 흐린다. 리뷰어끼리도 통신하지 않는다 — 같은 결함을 두 관점에서 독립적으로 보는 것이 목적이다.

## 간소화 원칙

이 리뷰가 빠른 이유는 셋이다. 어길 때마다 비용이 배로 늘어난다.

1. **범위는 diff다.** 변경된 파일과 그 경계면 반대쪽만 읽는다. 코드베이스 전반의 품질 감사를 하지 않는다
2. **라운드는 1회다.** 발견을 모아 한 번에 보고한다. 차단 항목을 고친 뒤에는 **그 항목만** 재확인한다. 전체 리뷰를 다시 돌리지 않는다
3. **차단만 필수다.** 발견을 3등급으로 나누고, 차단만 수정 후 진행 조건으로 삼는다

| 등급 | 의미 | 처리 |
|------|------|------|
| **차단** | 런타임 실패·데이터 손상·계획 요구사항 미충족 | 수정 필수 |
| **권고** | 지금 고치는 게 싸지만 동작은 한다 | 사용자 판단 |
| **관찰** | 기록해둘 사실 | 학습 후보로 넘김 |

## Phase 1: 위험도 판정 (Tier)

리뷰어를 몇 명 돌릴지 먼저 정한다. 판정 입력:
- 계획의 `## 경계면 영향` 섹션
- `_workspace/<plan-slug>/02_work_summary.md`의 `경계면 변경` / `계획과 달라진 점`
- `git diff --stat <base>` — 변경 파일 목록

```bash
git diff --stat HEAD~<커밋수>     # 또는
git diff --stat main...HEAD
```

**Tier 2 (리뷰어 2명 병렬)** — 아래 중 **하나라도** 참이면:

| 신호 | 확인 방법 |
|------|----------|
| 계획의 `경계면 영향`에 "예"가 하나 이상 | 계획 읽기 |
| diff에 `src/lib/api/` 변경 포함 | 파일 목록 |
| diff에 `src/lib/types.ts` 변경 포함 | 파일 목록 |
| diff에 `.env*`, `next.config.ts`, `package.json` 변경 포함 | 파일 목록 |
| `src/app/**/page.tsx` 추가·삭제·이동 (라우트 변경) | 파일 목록 |
| `../backend/` 또는 `../core/` 파일 변경 포함 | 파일 목록 |
| 구현 요약에 `경계면 변경` 항목이 비어 있지 않음 | 요약 읽기 |
| 구현 요약에 `테스트 없음 예외`가 있음 | 요약 읽기 |
| 변경 파일 10개 초과 | `--stat` 합계 |

**Tier 1 (리뷰어 1명)** — 위 신호가 전부 거짓일 때. 컴포넌트 내부·스타일·문구·문서 변경이 대표적이다.

판정을 사용자에게 한 줄로 알린다: `리뷰 Tier 2 — <발동 신호>. 리뷰어 2명 병렬.`

## Phase 2: 리뷰 실행

### Tier 1

`boundary-reviewer`만 호출한다 (`model: "opus"`). 경계면이 안 움직였어도 이 리뷰어를 쓰는 이유: 계획 대비 누락·범위 초과 확인이 그의 역할에 포함되고, 그것이 Tier 1에서 가장 자주 나오는 결함이다.

프롬프트에 검증 명령 실행을 추가 지시한다 — Tier 1에는 regression-reviewer가 없으므로 최소 회귀 확인이 필요하다:
```bash
npx tsc --noEmit && npm run test
```

### Tier 2

한 메시지에서 두 리뷰어를 동시에 호출한다 (`run_in_background: true`, `model: "opus"`).

| 리뷰어 | subagent_type | 관점 | 출력 |
|--------|--------------|------|------|
| 경계면 | `boundary-reviewer` | 계약 일치 교차 검증, 계획 대비 누락 | `03_review_boundary.md` |
| 회귀 | `regression-reviewer` | 검증 명령 실행, 테스트 공백 | `03_review_regression.md` |

두 프롬프트에 공통으로 포함할 것:
- 계획 파일 절대 경로
- 변경 파일 목록 (`git diff --stat` 출력 원문)
- `_workspace/<plan-slug>/02_work_summary.md` 경로
- **계획의 `## 최종 검증` 절 전문**
- 산출물을 쓸 절대 경로
- 리뷰 범위 제한 명시: "이 diff와 그 경계면 반대쪽만. 코드베이스 전반 감사 금지"

### 계획의 `## 최종 검증` 절을 반드시 실행한다

이 절은 장식이 아니라 **오케스트레이터가 파싱하는 인터페이스**다. 게이트 명령(`test`·`tsc`·`lint`·`build`)뿐 아니라 **그 계획에서만 아는 실측 항목**이 들어 있다 — env 없이 빌드가 통과하는지, 추가한 테스트 파일명이 실행 출력에 실제로 찍히는지, 사람이 브라우저로 확인해야 하는 항목 등.

절이 없거나 비어 있으면 게이트를 임의로 구성해 대체하지 말고, **계획에 그 절이 없다는 사실을 보고에 명시한다.** 임의 구성으로는 계획만 아는 실측 항목이 복원되지 않아, "실측해야 한다"고 판단된 것이 조용히 검증에서 빠진다.

경계면 체크리스트가 필요하면 `references/boundary-checklist.md`를 읽어 프롬프트에 관련 항목만 발췌해 넣는다. 전체를 넣으면 리뷰어가 무관한 경계면까지 훑는다.

## Phase 3: 통합 보고

두 리뷰어의 발견을 하나로 합친다. 중복 발견(같은 파일·같은 원인)은 하나로 묶고 양쪽 근거를 병기한다. 상충하는 판정은 삭제하지 않고 양쪽을 명시한다 — 어느 쪽이 맞는지는 사용자가 코드를 보고 판단한다.

```
리뷰 완료 (Tier <n>) — 차단 N / 권고 N / 관찰 N

## 차단 (수정 필요)
1. **<제목>** `경로:라인`
   - 깨지는 경로: <어떤 상황에서 무엇이 실패>
   - 수정: <방향>

## 권고
1. **<제목>** `경로:라인` — <한 줄>

## 관찰
- <한 줄>

## 검증 결과
- `npx tsc --noEmit` → <결과>
- `npm run test` → <결과>
- <Tier 2일 때 lint/build>

## 최종 검증 (계획의 해당 절)
| 항목 | 결과 |
|------|------|
| <계획이 지정한 실측 항목> | 통과 / 실패 / 미실행(이유) |
| <사람이 확인해야 하는 항목> | 사용자 확인 필요 |

<계획에 그 절이 없으면: "계획에 `## 최종 검증` 절 없음 — 게이트 명령만 실행함">

## 검증하지 못한 것
- <없으면 "없음">

차단 항목을 수정할까요?
```

`AskUserQuestion` 선택지: "차단 수정 / 차단+권고 모두 수정 / 이대로 진행".

## Phase 4: 수정과 재확인

차단 수정이 승인되면:

1. 발견을 **파일 단위로 묶는다**. 한 파일의 여러 발견은 한 번의 수정으로 처리한다
2. 해당 유닛의 `unit-implementer`를 재호출한다 (`model: "opus"`). 프롬프트에 지적된 발견만 전달하고 "지적 범위 밖 코드를 개선하지 말 것"을 명시한다
3. 수정 후 **그 항목만** 재확인한다. 전체 리뷰를 다시 돌리지 않는다:
   - 리더가 직접 해당 파일의 경계면 양쪽을 읽고 확인
   - `npx tsc --noEmit && npm run test` 재실행
4. 수정을 커밋한다 (승인 후). 커밋 메시지: `fix(<scope>): <리뷰 지적 내용>`

재리뷰가 정당한 경우는 하나다: 수정이 **새 경계면을 건드렸을 때**. 그때는 Tier 판정을 다시 하고 해당 리뷰어만 재호출한다.

## 데이터 흐름

```
계획 + 02_work_summary.md + git diff --stat
    ↓
[Tier 판정]
    ├─ Tier 1 ─→ [boundary-reviewer] ────────────────┐
    └─ Tier 2 ─→ [boundary-reviewer]   ─┐            │
                 [regression-reviewer] ─┤ (병렬)      │
                                        ↓            ↓
                        03_review_boundary.md / 03_review_regression.md
                                        ↓
                                  [리더: 통합 보고]
                                        ↓
                                  사용자 판단 게이트
                                        ↓
                            [unit-implementer 재호출] → 해당 항목만 재확인
```

## 에러 핸들링

| 상황 | 전략 |
|------|------|
| 리뷰어 1명 실패 | 1회 재시도. 재실패 시 나머지 결과로 보고하고 "<관점> 미검증"을 보고에 명시. 리뷰 없이 통과시키지 않는다 |
| diff 범위를 알 수 없음 (커밋 이력 불명확) | `git status` + `git diff HEAD`로 파악. 실패 시 계획의 유닛 `파일` 목록을 범위로 삼고 그 사실을 명시 |
| 차단이 5건 초과 | 개별 나열을 멈추고 공통 원인을 찾는다. 계획 전제가 틀렸을 가능성이 크므로 사용자에게 계획 수정을 제안한다 |
| 두 리뷰어 판정이 상충 | 어느 쪽도 지우지 않는다. 양쪽 근거를 병기해 보고하고 사용자가 판단하게 한다 |
| 수정 후 새 차단이 나타남 | 1회는 수정 루프를 허용한다. 2회 연속 새 차단이 나오면 멈추고 사용자에게 보고한다 — 무한 루프를 방지한다 |
| 리뷰 대상 변경이 없음 (diff 비어 있음) | 리뷰어를 호출하지 않는다. "변경 없음"을 보고하고 종료 |

## 테스트 시나리오

### 정상 흐름 (Tier 1)
1. 변경: `src/components/planner/PlaceCard.tsx` 스타일 조정 2파일
2. Phase 1: 경계면 신호 전부 거짓 → Tier 1
3. Phase 2: `boundary-reviewer` 1명 + `tsc --noEmit`, `npm run test` 실행
4. Phase 3: 차단 0 / 권고 1 (반복되는 클래스 문자열을 상수로) / 관찰 0
5. 사용자가 "이대로 진행" 선택 → 종료
6. 예상 결과: 리뷰 산출물 1개, 총 리뷰어 1명

### 정상 흐름 (Tier 2)
1. 변경: `src/lib/api/itinerary.ts` + `src/lib/types.ts` + 컴포넌트 3개
2. Phase 1: `src/lib/api/` 및 `types.ts` 변경 → Tier 2. 사용자에게 판정 통보
3. Phase 2: 두 리뷰어 병렬. boundary가 "백엔드 DTO의 `message` 필드와 프론트 파서 기대 불일치" 확정 차단 1건 보고, regression이 "`readErrorMessage` 새 분기에 테스트 없음" 권고 1건
4. Phase 3: 차단 1 / 권고 1 통합 보고
5. Phase 4: 차단 수정 → 해당 파일 경계면 재확인 + `tsc`/`test` 재실행 → 커밋
6. 예상 결과: 리뷰 산출물 2개 + 수정 커밋 1개

### 에러 흐름
1. Tier 2에서 `regression-reviewer`가 `npm run test` 실행 중 기존 실패 12건을 발견
2. 리뷰어가 `git stash` 후 재실행으로 "이번 변경 전에도 실패" 확인 → "기존 실패, 범위 밖"으로 분류
3. 통합 보고에 관찰로 기록하고 차단으로 올리지 않는다
4. 리더가 사용자에게 "기존 실패 12건 존재 — 별도 계획 필요"를 함께 보고
