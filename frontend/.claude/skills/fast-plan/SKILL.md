# Fast Plan — spec 없이 바로 구현 계획

요청에서 곧바로 실행 가능한 구현 계획 하나를 만든다. 요구사항 문서를 선행 산출물로 만들지 않는다.

## 실행 모드: 서브 에이전트

스카우트 2명을 병렬로 돌린 뒤 계획 작성자 1명을 호출한다. 세 에이전트 사이에 실시간 통신이 필요 없고(조사 → 작성의 단방향 흐름), 결과만 파일로 전달되면 충분하므로 팀 오버헤드를 쓰지 않는다.

## 에이전트 구성

| 에이전트 | subagent_type | model | 역할 | 출력 |
|---------|--------------|-------|------|------|
| codebase-scout | `codebase-scout` | opus | 관련 파일·패턴·경계면 조사 | `01_scout_codebase.md` |
| learning-scout | `learning-scout` | opus | 과거 학습·이전 계획·이력 조사 | `01_scout_learnings.md` |
| plan-architect | `plan-architect` | opus | 계획 문서 작성 | `docs/plans/...-plan.md` |

## 워크플로우

### Phase 0: 컨텍스트 확인

1. `docs/plans/`를 확인해 이 요청과 관련된 계획이 이미 있는지 본다
2. 실행 모드를 결정한다:

| 상황 | 모드 | 행동 |
|------|------|------|
| 관련 계획 없음 | **초기 실행** | Phase 1부터 진행 |
| 관련 계획 있음 + 사용자가 수정·보완 요청 | **갱신** | 스카우트를 건너뛰고 plan-architect만 호출. 기존 파일을 갱신 (새 파일 금지) |
| 관련 계획 있음 + 새 요청 | **신규** | 사용자에게 "기존 계획 `<경로>`와 겹칩니다. 갱신할까요, 새로 만들까요?"를 확인한 뒤 진행 |

갱신 모드에서 U-ID를 재번호하지 않는다. 구현·리뷰 기록이 U-ID로 계획을 참조하므로 재번호는 추적을 끊는다.

### Phase 1: 준비

1. 요청에서 계획 유형(`feat`/`fix`/`refactor`/`chore`)과 slug(3~5단어 kebab-case)를 정한다
2. 계획 파일 경로를 확정한다: `docs/plans/YYYY-MM-DD-NNN-<type>-<slug>-plan.md`
   - 날짜는 오늘. `NNN`은 같은 날짜의 기존 파일을 확인해 다음 순번 (001부터 3자리)
3. 작업 디렉토리를 만든다: `.claude/_workspace/<plan-slug>/` (`<plan-slug>`은 계획 파일명에서 `-plan.md`를 뗀 값)

### Phase 2: 병렬 조사

한 메시지에서 두 에이전트를 동시에 호출한다 (`run_in_background: true`, `model: "opus"`).

각 에이전트 프롬프트에 반드시 포함할 것:
- 사용자 요청 원문
- 산출물을 쓸 절대 경로 (`.claude/_workspace/<plan-slug>/01_scout_*.md`)
- 조사 초점 힌트 — 요청에서 추론한 관련 영역 (예: "chat API 에러 처리 경로", "일정 타임라인 컴포넌트")

조사를 건너뛰어도 되는 경우: **없다.** 요청이 사소해 보여도 이 프로젝트의 Next.js 버전 사실과 기존 패턴 확인이 필요하다. 다만 요청이 단일 파일의 명백한 오타·상수 변경이면 스카우트 없이 계획 없이 바로 고치는 것이 맞다 — 그때는 이 스킬을 쓰지 않는다.

### Phase 3: 계획 작성

두 스카우트가 끝나면 plan-architect를 호출한다 (`model: "opus"`).

프롬프트에 포함할 것:
- 사용자 요청 원문
- 두 스카우트 산출물의 절대 경로 (에이전트가 Read로 읽는다)
- 확정된 계획 파일 절대 경로
- 갱신 모드일 때: 기존 계획 경로 + 사용자 피드백

### Phase 4: 확인 게이트

계획 작성이 끝나면 사용자에게 확인받는다. 이 게이트를 건너뛰지 않는다 — 잘못된 계획으로 구현에 들어가면 되돌리는 비용이 계획 재작성보다 훨씬 크다.

보고 형식:

```
계획 완료: docs/plans/<파일명>

**범위:** <한 줄>
**유닛:** N개 — U1 <제목> / U2 <제목> / ...
**경계면 변경:** <있는 것만 나열, 없으면 "없음">
**리스크:** <최상위 1~2개>
**구현 시점 결정 사항:** N건
**최종 검증 항목:** N건 (사람 확인 필요 N건)

이대로 진행할까요?
```

보고하기 전에 계획에 `## 최종 검증` 절이 있는지 확인한다. **없으면 plan-architect에게 추가를 요청한다** — 이 절은 리뷰 단계가 파싱하는 인터페이스이고, 없으면 리뷰가 게이트를 임의로 구성해 대체하면서 계획만 아는 실측 항목이 조용히 빠진다. 유닛이 2개뿐인 작은 계획도 예외가 아니다.

`AskUserQuestion`으로 물을 때 선택지는 "이대로 구현 시작 / 계획 수정 / 범위 축소"를 제시한다.

## 데이터 흐름

```
사용자 요청
    ├──→ [codebase-scout] ──→ 01_scout_codebase.md ──┐
    └──→ [learning-scout] ──→ 01_scout_learnings.md ─┤
                                                      ↓
                                            [plan-architect]
                                                      ↓
                                    docs/plans/...-plan.md
                                                      ↓
                                              사용자 확인 게이트
```

## 에러 핸들링

| 상황 | 전략 |
|------|------|
| 스카우트 1명 실패 | 1회 재시도. 재실패 시 나머지 결과로 계획을 작성하고, 계획 `## 리스크`에 "조사 범위 제한(<어느 조사>)" 명시 |
| 스카우트 둘 다 실패 | plan-architect에게 "스카우트 산출물 없음 — 직접 최소 조사 후 작성" 지시. 계획에 조사 제한을 명시 |
| plan-architect가 유닛 분해 불가 | 계획을 쓰되 모호한 지점을 `## 구현 시점에 결정할 것`으로 옮긴다. 사용자에게 "무엇이 결정되면 유닛이 확정되는가"를 질문 |
| 유닛이 10개 초과 | 억지로 합치지 않는다. 사용자에게 규모를 보고하고 범위 축소 여부를 결정하게 한다 |
| `docs/plans/`에 같은 날짜·같은 slug 파일 존재 | 순번을 올린다. 덮어쓰지 않는다 |

## 테스트 시나리오

### 정상 흐름
1. 사용자: "채팅 에러 메시지를 토스트로 보여주고 싶어"
2. Phase 0: `docs/plans/` 확인 → 관련 계획 없음 → 초기 실행
3. Phase 1: `docs/plans/2026-07-29-001-feat-chat-error-toast-plan.md` 확정, `.claude/_workspace/2026-07-29-001-feat-chat-error-toast/` 생성
4. Phase 2: 두 스카우트 병렬 → `src/lib/api/itinerary.ts`의 에러 문구 상수, `ChatPanel.tsx` 현재 에러 표시 방식, `docs/solutions/` 미존재 확인
5. Phase 3: plan-architect가 3개 유닛으로 분해 (토스트 컴포넌트 / 에러 상태 훅 분리 / ChatPanel 연결)
6. Phase 4: 사용자 확인 → 승인
7. 예상 결과: 계획 파일 1개 + `_workspace/` 조사 2개

### 에러 흐름
1. 사용자 요청이 backend API 신규 엔드포인트에 의존
2. Phase 2: codebase-scout가 "대응 백엔드 엔드포인트 미존재"를 보고
3. Phase 3: plan-architect가 이를 `## 리스크` 최상위로 올리고, frontend 범위만으로 완결되는 유닛과 backend 의존 유닛을 분리
4. Phase 4: 사용자에게 "backend 작업이 선행되어야 하는 유닛 N개 — 범위를 frontend로 좁힐까요?" 확인
5. 계획은 생성되고, 차단 요인이 문서에 남는다
