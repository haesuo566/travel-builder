# Dev Flow — plan → work → review → compound

travel-buider frontend의 개발 작업을 네 단계로 조율한다. 각 단계는 개별 스킬로 분리되어 있어 단독 호출도 가능하다.

## 실행 모드: 서브 에이전트

**이 환경에는 `TeamCreate`가 없다.** 에이전트 팀 모드(팀원 간 자체 조율, 공유 작업 목록 claim)를 전제한 설계는 호출 시점에 실패한다. 모든 단계를 `Agent` 도구 기반 서브 에이전트로 조율한다.

| 수단 | 용도 |
|------|------|
| `Agent`(한 메시지에 여러 호출) | 병렬 실행 |
| `Agent`의 `name` | 실행 중 에이전트를 주소 지정 가능하게 만든다 |
| `SendMessage({to: name})` / 에이전트→`{to: "main"}` | 리더 경유 양방향 전달 |
| 반환값 | 결과 수집 |
| 파일 (`_workspace/`) | 대용량 산출물, 단계 간 인계, 감사 추적 |
| `TaskCreate`/`TaskUpdate` | 진행 상황 노출 |

| Phase | 병렬성 | 구성 |
|-------|--------|------|
| 1. Plan | 스카우트 2명 병렬 → 작성 1명 순차 | 조사 → 작성의 단방향 흐름 |
| 2. Work | 파일 겹침 없는 유닛만 병렬 (최대 3) | 경계면 변경은 리더 경유 전달 |
| 3. Review | 위험도에 따라 1~2명 병렬 | 격리된 독립 판단 |
| 4. Compound | 1명 | 단발성 문서화 |

## 단계 구성

| Phase | 스킬 | 산출물 | 게이트 |
|-------|------|--------|--------|
| 1. Plan | `fast-plan` | `docs/plans/<...>-plan.md` | 계획 승인 |
| 2. Work | `unit-work` | 코드 변경 + 커밋 + `02_work_summary.md` | 유닛별 커밋 승인 |
| 3. Review | `lite-review` | `03_review_*.md` | 차단 수정 판단 |
| 4. Compound | `capture-learning` | `docs/solutions/<...>.md` + 하네스 개선 | 하네스 수정 승인 |

각 Phase는 `Skill` 도구로 해당 스킬을 호출해 진행한다. 스킬 내용을 여기서 중복 설명하지 않는다.

## 작업 디렉토리

```
docs/plans/YYYY-MM-DD-NNN-<type>-<slug>-plan.md    계획 (커밋 대상, A 경로만)
docs/solutions/<category>/<slug>.md                 학습 (커밋 대상, A 경로만)
.claude/_workspace/quick-log.md                     B 경로 전용. 실행당 한 줄. 다음 A 실행의 capture-learning이 읽는다
.claude/_workspace/<plan-slug>/                     중간 산출물 (git 무시, A 경로만)
├── 01_scout_codebase.md
├── 01_scout_learnings.md
├── 02_work_summary.md
├── 03_review_boundary.md
└── 03_review_regression.md
```

`<plan-slug>`은 계획 파일명에서 `-plan.md`를 뗀 값이다. **`_workspace/`를 삭제하지 않는다** — 리뷰와 학습 단계가 이전 단계의 판단 근거를 읽는다. `quick-log.md`는 특정 `<plan-slug>` 하위가 아니라 `_workspace/` 바로 밑에 둔다 — B 경로에는 plan-slug가 없고, 이 파일은 여러 B 실행에 걸쳐 누적돼야 패턴이 보인다.

## Phase 0: 컨텍스트 확인

**어느 단계부터 시작할지 먼저 판정한다.** 건너뛰고 Phase 1부터 시작하면 이미 있는 계획을 덮어쓰거나 이미 구현된 유닛을 다시 구현한다.

1. `docs/plans/`에서 이 요청과 관련된 계획을 찾는다
2. 계획이 있으면 `.claude/_workspace/<plan-slug>/` 산출물과 `git log --oneline -20`을 확인한다
3. **`git status`가 더러우면 재개 지점을 정하기 전에 미커밋 변경을 분류한다.** 파일 단위가 아니라 hunk 단위로 계획과 대조한다:

   | 분류 | 판단 기준 | 조치 |
   |------|----------|------|
   | 진행분 | 계획의 어느 유닛 블록과 일치 | 검증 후 그 유닛으로 커밋 |
   | 근거 없는 변경 | 계획에도 HEAD에도 근거 없음 | 원복하고 기록 |

   두 형태의 겉모습(`git diff`에 변경이 있다)이 같아서, 분류 없이 이어가면 어느 쪽이든 한 번에 잘못 확정된다. 이 리포에서 실제로 핸들러 호출이 뒤바뀐 stray 변경이 발견됐고 **테스트는 초록불이었다.** 상세 절차는 `unit-work` Phase 0에 있다.

4. 진입점을 결정한다:

| 상태 | 진입점 | 행동 |
|------|--------|------|
| 관련 계획 없음 | **Phase 1** | 전체 흐름 |
| 계획 있음, 구현 커밋 없음 | **Phase 2** | "계획 `<경로>` 발견 — 이대로 구현할까요?" 확인 후 진행 |
| 계획 + 일부 유닛 커밋됨 | **Phase 2 (이어서)** | 미구현 유닛만 |
| 계획 + 전 유닛 커밋, 리뷰 산출물 없음 | **Phase 3** | 리뷰부터 |
| 계획 + 구현 + 리뷰 완료 | **Phase 4** | 학습 정리 |
| 사용자가 단계를 명시 ("리뷰만", "구현만") | 해당 Phase | 그 단계만 실행하고 종료. 다음 단계를 자동으로 이어가지 않는다 |
| 사용자가 계획 수정 요청 | **Phase 1 (갱신)** | 기존 계획 갱신 후 Phase 2 재개 |

판정 결과를 한 줄로 알린다: `Phase <n>부터 시작 — <근거>.`

## 게이트 0 — 경로 선택

**Phase 0의 진입점이 Phase 1(새 계획 생성 또는 계획 갱신)로 판정된 경우에만 실행한다.** Phase 2~4로 이어가는 경우(이미 계획이 있고 일부·전부 구현된 경우)는 건너뛴다 — 그 계획을 만들 때 이미 경로가 확정됐고, 중간에 흐름을 바꾸면 유닛·리뷰·학습이 어느 계획에 속하는지 추적이 끊긴다.

Phase 1 진입이 확정되면, `fast-plan`을 호출하기 전에 **먼저** `AskUserQuestion` 하나로 사용자에게 경로를 고르게 한다. 스카우트 에이전트를 스폰하기 전이어야 한다 — 질문 없이 조사부터 시작하면 B를 선택했을 때 그 조사 비용이 버려진다. (backend `tb-harness`의 게이트 0과 같은 설계 — 두 하네스가 같은 어휘를 쓴다)

| 경로 | 무엇이 도는가 | 산출물 |
|------|--------------|--------|
| **A. 전체 harness** | Phase 1 → 2 → 3 → 4 (`fast-plan` → `unit-work` → `lite-review` → `capture-learning`) | 계획 문서 · 커밋 · 리뷰 산출물 · 학습 |
| **B. 바로 구현** | `unit-implementer` 하나 → 검증 3~4종 → 커밋 | 커밋 · `quick-log.md` 한 줄 |

**B는 계획·리뷰·학습을 전부 생략한다.** 남는 안전망은 검증(`npx tsc --noEmit`·`npm run lint`·`npm test`·필요시 `npm run build`)과 구현자의 작업 원칙뿐이다. 사용자가 그 절충을 명시적으로 고른 것이므로 **리뷰를 몰래 끼워 넣지 않는다.**

**추천을 붙여서 묻는다.** 사용자가 뒤집을 수 있지만 판단 근거는 제시한다.

| 이런 변경이면 | 추천 | 왜 |
|--------------|------|-----|
| 새 파일·새 모듈·외부 연동(API·라우트) 추가 | **A** | 되돌릴 거리가 멀고 설계 결정이 남는다 |
| 공유 타입(`src/lib/types.ts`)·API 계약(`src/lib/api/*`)·라우트 변경 | **A** | 경계면 짝이 있고 타입 시스템이 그 짝을 연결해주지 않는다 |
| 에러 처리 분기·폴백 경로 신설 | **A** | 조용히 실패하는 종류다 — 응답이 200이고 화면도 정상이라 관측이 로그 한 줄에 걸린다 |
| 기존 파일 국소 수정(상태 추가 + 조건부 렌더링 재배선 등) · 문구·상수 변경 | **B** | |
| 테스트만 추가 · 주석 정리 | **B** | |
| 리뷰가 이미 지적한 것을 고치는 후속 | 게이트 없음 | 진행 중인 실행의 수정 루프다 |

### B 경로 실행 절차

1. **`unit-implementer`를 띄운다. 리더가 직접 짜지 않는다.** 계획 파일이 없으므로 목표·대상 파일·따를 패턴·테스트 시나리오·검증 명령을 리더가 프롬프트에 인라인으로 작성해 전달한다 — `unit-implementer`의 입력 프로토콜(계획 파일 경로 + U-ID)을 계획 없이 즉석으로 채우는 것이다.
2. `.claude/_workspace/<plan-slug>/`를 만들지 않는다. 대신 `.claude/_workspace/quick-log.md`에 **한 줄** append한다:
   `- {YYYY-MM-DD} {커밋 해시} {요청 한 줄 요약} — {변경 파일 수}개 파일`
   이 한 줄이 다음 A 경로 실행에서 `capture-learning`의 입력이 된다. **B가 남발되면 여기에 같은 성질의 수정이 쌓이고, 그 자체가 "계획이 필요했다"는 증거가 된다.**
3. **검증이 실패하면 커밋하지 않고 사용자에게 보고한다.** B에는 리뷰가 없으므로 여기서 넘기면 아무도 잡지 않는다.
4. UI 변경이면 가능한 경우 브라우저로 실제 동작을 확인한다.
5. 커밋은 여전히 사용자가 명시적으로 요청할 때만 한다.
6. 구현자가 "계획이 필요하다"·"경계면 영향이 있다"고 보고하면 **A로 승격한다.** 사용자에게 알리고 Phase 1부터 시작한다 — B에서 억지로 밀지 않는다. 승격은 실패가 아니라 게이트가 제 역할을 한 것이다.

**이 게이트는 매번 다시 묻는다** — 한 세션에서 한 번 B를 선택했다고 이후 요청까지 자동으로 생략하지 않는다. 요청마다 규모와 리스크가 다르기 때문이다.

## 이 흐름을 쓰지 않아야 할 때

계획·리뷰·학습의 비용이 변경 자체보다 큰 경우가 있다. 아래는 이 흐름 없이 바로 고친다:

- 단일 파일의 오타·문구·상수 값 변경
- 자명한 타입 오류 수정 (1~2줄)
- 사용자가 이미 정확한 변경 내용을 지시한 경우

판단이 애매하면 흐름을 쓴다. 계획 하나를 낭비하는 비용이 잘못된 구현을 되돌리는 비용보다 작다.

## Phase 1: Plan

`Skill` 도구로 `fast-plan`을 호출한다. 사용자 요청 원문을 인자로 전달한다.

**게이트:** 계획 완료 후 사용자 승인. 승인 없이 Phase 2로 넘어가지 않는다.

계획에 `## 최종 검증` 절이 있는지 확인한다. **없으면 Phase 3이 게이트를 임의로 구성해 대체하게 되고, 계획만 아는 실측 항목이 조용히 검증에서 빠진다.** 없으면 `fast-plan`에 그 절 추가를 요청한다.

반환된 계획 경로와 `<plan-slug>`를 이후 Phase에 전달한다.

## Phase 2: Work

`Skill` 도구로 `unit-work`를 호출한다. 계획 경로를 인자로 전달한다.

**게이트:** 유닛별 커밋 승인 (`unit-work` 내부에서 처리). 사용자가 "이후는 묻지 말고 진행"이라고 하면 그 세션 동안 생략한다.

병렬 배치 중 구현자가 `SendMessage({to: "main"})`으로 경계면 변경을 알리면, 실행 중인 다른 구현자에게 즉시 전달한다. 이것이 이 환경에서 유일한 경계면 조율 경로다.

## Phase 3: Review

`Skill` 도구로 `lite-review`를 호출한다. 계획 경로 + `<plan-slug>`를 전달한다.

`lite-review`가 위험도(Tier)를 판정해 리뷰어 수를 정한다. 리더가 리뷰어 수를 지정하지 않는다 — 판정 입력(계획의 경계면 영향, 구현 요약의 경계면 변경, diff 파일 목록)이 그 스킬 안에 있다.

계획의 `## 최종 검증` 절을 `lite-review`에 함께 전달한다. 그 절의 실측 항목은 게이트 명령으로 복원되지 않는다.

**게이트:** 차단 항목 수정 여부 사용자 판단.

## Phase 4: Compound

`Skill` 도구로 `capture-learning`을 호출한다. 계획 경로 + `<plan-slug>` + **이번 세션에서 실제로 막혔던 지점**을 전달한다. 마지막 항목이 가장 중요하다 — 파일에 남지 않고 리더의 대화 맥락에만 있다.

**게이트:** 하네스 개선 제안 적용 여부 사용자 판단.

## 최종 보고

네 단계가 끝나면 한 번에 요약한다.

```
작업 완료: <계획 제목>

**계획** docs/plans/<파일명> — 유닛 N개
**구현** N커밋 (브랜치 `<이름>`) — <핵심 변경 한 줄>
**리뷰** Tier <n> — 차단 N(수정 N) / 권고 N(반영 N) / 관찰 N
**최종 검증** <계획의 최종 검증 절 항목별 결과>
**학습** docs/solutions/<경로> (또는 "학습 없음 — 이유")
**하네스 개선** N건 적용 (또는 "없음")

**미완료**
- <끝내지 못한 것 + 이유. 없으면 "없음">

**다음 단계 제안**
- <PR 생성, 남은 유닛, 별도 계획이 필요한 발견 등>
```

미완료 항목을 보고에서 빼지 않는다. 축소된 범위를 완료로 보고하는 것이 이 흐름의 유일한 치명적 실패다.

## 데이터 흐름

```
사용자 요청
    ↓
[Phase 0: 진입점 판정] ─── 계획/커밋/리뷰 산출물 + 미커밋 diff 분류
    ↓ (Phase 1 진입 확정 시에만)
[게이트 0: A/B 경로 선택] ─── AskUserQuestion, 추천 붙여서 제시
    ├─ B: 바로 구현 ──→ unit-implementer(계획 없이) → 검증 → quick-log.md 한 줄 → (승인 시) 커밋 → 종료
    └─ A: 전체 harness
         ↓
[Phase 1: fast-plan]
  codebase-scout ─┐ (병렬)
  learning-scout ─┴→ plan-architect → docs/plans/...-plan.md
    ↓ 계획 승인 게이트
[Phase 2: unit-work]
  unit-implementer × N (파일 겹침 없으면 병렬, name 지정)
    ↑ 경계면 변경 SendMessage({to:"main"}) ──→ [리더] ──→ 다른 구현자에 전달
    ↓ 유닛별 커밋 승인 게이트
```

## 에러 핸들링

| 상황 | 전략 |
|------|------|
| Phase 1에서 계획 분해 불가 | 계획을 쓰되 모호한 지점을 `구현 시점에 결정할 것`으로 옮긴다. 사용자에게 무엇이 결정되면 확정되는지 질문. Phase 2로 넘어가지 않는다 |
| 계획에 `## 최종 검증` 절이 없음 | Phase 3에 넘기기 전에 추가를 요청한다. 임의 게이트로 대체하지 않는다 |
| Phase 0에서 근거 없는 미커밋 변경 발견 | 원복하고 기록한다. "원인 불명이라 유지"는 선택지가 아니다 |
| Phase 2에서 유닛 절반 이상 차단 | 계획 전제 문제 신호다. 구현을 계속하지 않고 사용자에게 계획 재작성 여부를 확인한다 |
| Phase 2에서 구현자가 계획과 다르게 구현 | 되돌리지 않는다. `02_work_summary.md`의 `계획과 달라진 점`에 기록하고 Phase 3이 그 지점을 우선 확인하게 한다 |
| Phase 3 차단이 5건 초과 | 공통 원인을 찾는다. 계획 전제 문제일 가능성이 크므로 사용자에게 계획 수정을 제안한다 |
| Phase 3에서 수정 후 새 차단 반복 | 수정 루프를 1회만 허용한다. 2회 연속 새 차단이 나오면 멈추고 보고한다 |
| Phase 4에서 남길 학습 없음 | 정상 결과다. "학습 없음 — 이유"로 보고하고 종료 |
| 중간 Phase에서 사용자가 중단 | `_workspace/`를 보존한다. 다음 호출 시 Phase 0이 진입점을 판정해 이어간다 |
| `_workspace/` 산출물이 계획과 불일치 | 덮어쓰지 않는다. `<plan-slug>`는 계획 파일명에서 도출되므로 불일치는 slug 계산 오류다. 다시 도출한다 |

## 테스트 시나리오

### 정상 흐름 (전체 4단계)
1. 사용자: "채팅 에러를 토스트로 보여주고 싶어"
2. Phase 0: 관련 계획 없음, 트리 깨끗 → Phase 1부터
3. 게이트 0: `AskUserQuestion`으로 경로 확인 → 경계면 변경(공유 타입) 가능성이 있어 **A를 추천** → 사용자가 A 선택
4. Phase 1: 스카우트 2명 병렬 → 계획 3유닛 + `## 최종 검증` 절 확인 → 사용자 승인
5. Phase 2: U1·U2 파일 겹침 없음 → 한 메시지에 `Agent` 2개 병렬. `impl-u1`이 `types.ts` 변경을 `{to:"main"}`으로 알림 → 리더가 `impl-u2`에 전달. 유닛별 커밋 3회
6. Phase 3: 구현 요약에 `types.ts` 경계면 변경 기록됨 → Tier 2. 리뷰어 2명 병렬 → 차단 1 / 권고 1. 계획의 최종 검증 실측 항목까지 확인. 차단 수정 → 해당 항목만 재확인 → 커밋
7. Phase 4: 학습 문서 1개(`boundary-issues/`) + 하네스 개선 1건 → 승인 → 체크리스트 수정 + CLAUDE.md 이력
8. 예상 결과: 계획 1 + 커밋 4 + 리뷰 2 + 학습 1 + 하네스 수정 1

### 후속 진입 흐름
1. 사용자: "어제 하던 토스트 작업 이어서"
2. Phase 0: 계획 발견, `git log`에 U1·U2 커밋 존재, 리뷰 산출물 없음. `git status` 더러움 → hunk 분류: U3 진행분 1건, 근거 없는 변경 1건(원복)
3. **Phase 2 (이어서)** 진입 판정, 사용자에게 통보
4. Phase 2: U3 진행분 검증 후 커밋 → 남은 부분 구현
5. Phase 3~4 정상 진행
6. 예상 결과: 중복 구현 없음, stray 변경이 커밋에 섞이지 않음

### 게이트 0에서 B 경로 선택
1. 사용자: "일정 패널에 토글 기능 추가해줘"
2. Phase 0: 관련 계획 없음 → Phase 1 진입 판정
3. 게이트 0: 기존 파일 국소 수정(상태 하나 추가 + 조건부 렌더링 재배선)이라 **B를 추천** → 사용자가 B 선택
4. `unit-implementer`를 계획 파일 없이(목표·대상 파일·검증을 리더가 인라인으로 작성) 스폰. 구현 후 `tsc`·`lint`·`test`·`build` + 가능하면 브라우저로 검증
5. `quick-log.md`에 한 줄 append. 계획·리뷰·학습 산출물 없음
6. 예상 결과: 계획 파일 0개, 커밋은 사용자가 요청할 때만, `_workspace/<plan-slug>/` 없음, `quick-log.md`에 1줄 추가

### 에러 흐름
1. Phase 2에서 U3 구현자가 "backend에 대응 엔드포인트가 없어 연결 불가" 차단 보고
2. 리더가 계획의 `## 리스크`를 확인 — 이 의존을 예측했는지 본다
3. 예측했다면: U3을 미완료로 두고 U1·U2만으로 Phase 3 진행. 리뷰 범위를 완료 유닛으로 한정
4. 예측하지 못했다면: 사용자에게 "backend 작업 선행 필요 — 범위를 좁힐까요, backend 계획을 먼저 세울까요?" 확인
5. Phase 4에서 "계획 단계에서 backend 의존을 확인하지 않았다"를 하네스 개선 제안으로 올린다 (`plan-architect`의 경계면 확인 강화)
6. 최종 보고의 `미완료`에 U3과 이유를 명시한다
