# 코드 리뷰 규약

리뷰의 목적은 **결함을 찾는 것**이지 코드에 의견을 남기는 것이 아니다. 지적 하나가 구현자의 시간을 태우므로, 태울 값어치가 있는 것만 낸다.

## 이 하네스의 review는 경량 단일 패스다

리뷰는 이 파이프라인에서 가장 비싼 단계다. 그래서 **다음 셋을 명시적으로 포기했다** — 사용자가 승인한 절충이며, 되돌리려 하지 말고 이 제약 안에서 최대한 잡는다.

| 포기한 것 | 결과 |
|---|---|
| 축 간 교차검증 (정확성·계약·테스트를 각각 다른 리뷰어가 봄) | 한 관점에 매몰되면 다른 관점의 결함을 놓친다 |
| 실행 기반 증명 (임시 테스트 작성, 구현 뮤테이션) | "이 테스트는 가짜로 통과한다"는 판정의 확신이 약하다 |
| 재검증 사이클 (수정 후 해소 판정) | 수정이 지적을 실제로 해소했는지 아무도 다시 확인하지 않는다 |

**확신이 약한 지적을 지우지는 않는다.** 정황이 뚜렷하면(예: assertion이 구현 문자열을 그대로 복사) 심각도를 낮춰서라도 남긴다.

## 검증 게이트 — 이걸 통과 못 한 지적은 버린다

**모든 지적은 구체적 실패 시나리오를 가져야 한다.**

```
입력/상태: {구체적인 값 또는 상황}
       ↓
잘못된 결과: {실제로 무슨 일이 일어나는가}
```

시나리오를 만들 수 없다면 그것은 결함이 아니라 **인상**이다. 인상은 적지 않는다.

**실행 증명이 생략된 것이지 이 게이트가 생략된 게 아니다.** 시나리오는 실행 없이 코드만 읽고도 쓸 수 있다.

시나리오는 **구현자가 재현할 수 있을 만큼 구체적이어야 한다.** 이 하네스에는 재검증이 없어서, 모호한 지적은 확인 없이 "고쳤다"로 닫힌다.

## 무엇을 실행하는가

```
npm test
npx tsc --noEmit -p tsconfig.json
npx eslint src --max-warnings=0
```

**1회 실행해 통과 여부만 확인한다.** 통과한다는 구현자의 주장을 그대로 받지 않는다. 새 테스트를 쓰지 않고 뮤테이션도 하지 않는다 — 그 대신 assertion이 실제로 그 로직을 검증하는지 **코드를 읽어** 판단한다.

임시로 만든 것은 **반드시 원복하고 커밋하지 않는다.**

## 리뷰 전에 반드시 하는 일

1. **계획을 실제로 읽는다.** 기억·추정으로 이탈을 판정하지 않는다. 계획 앞부분의 **설계 결정·에러 처리 표·범위 밖**이 판정 기준이다.
2. **diff만 보지 않는다.** 변경된 함수의 **호출자 전부**를 읽는다. 결함은 대개 변경된 줄이 아니라 그 변경이 깨뜨린 가정에 있다.
3. **`.claude/learnings/`를 읽는다.** 과거에 잡힌 유형이 이번에도 있는지 먼저 확인한다. 재발 유형은 새 결함보다 적발 확률이 높고 확인 비용이 낮다. (비어 있으면 건너뛴다)

## 우선순위 순서 — 시간이 부족하면 위에서부터만

1. **경계면 교차 비교** — DTO·엔티티·클라이언트 반환처럼 모듈 경계를 넘는 변경이 있으면 **양쪽 파일을 동시에 열어** shape을 대조한다. `"필드가 있는가"` 확인은 검증이 아니다. **한쪽만 인용한 지적은 교차 비교를 안 한 것이다.** 짝 목록은 `tb-tdd-implement/references/backend-constraints.md`의 경계 표에 있다.
2. **계획 이탈** — 태스크·시그니처와 실제 구현을 대조한다. 벗어난 것 자체보다 **벗어났는데 문서가 그대로인 것**이 문제다.
3. **정확성**
4. **테스트 품질**

## 체크리스트

| 축 | 본다 |
|---|---|
| 정확성 | 빈 값·null·0·경계값 / 상태 전이가 갈 수 없는 상태로 가는가 / **실패 책임을 잘못된 대상에 청구하는가** — 외부 서비스 장애를 사용자 입력 오류(400)로, 우리 설정이 만든 404를 상대 장애로 / 예외 경로 자원 정리 / 멱등성 |
| 계약 | 계획 대비 이탈(시그니처·범위 확장) / 경계 양쪽 shape 일치(snake_case↔camelCase, 타입은 같고 의미가 다른 값) / **같은 엔드포인트가 두 형태의 에러 바디를 낼 때 양쪽이 다뤄지는가** |
| 테스트 | 성공만 있고 실패 케이스 없음(대칭 누락) / **형제 파일에는 있는 테스트가 이 파일에 없음** / 구현 문자열을 그대로 베낀 assertion / 수정 커밋에 회귀 테스트가 붙었는지 / `toBeDefined()`류 약한 단정 / **부재를 검증한다는 테스트가 로컬 `.env` 때문에 가짜로 통과하는가** |

**"상위 모듈 테스트가 있으니 됐다"는 대체재가 아니다.** 먼저 던지는 프로바이더가 단정을 만족시켜 하위 경로가 안 밟혀도 초록불이 된다.

## 심각도

| 등급 | 기준 | 처리 |
|---|---|---|
| **Critical** | 데이터 손상·유실, 소멸성 자원 낭비, 정상 데이터의 영구 제외, 보안 | 즉시 수정. 다음 묶음으로 진행 금지 |
| **Major** | 특정 입력에서 잘못된 결과, 복구 불가능한 상태, 테스트가 검증하지 못하는 핵심 경로 | 이번 묶음 안에서 수정 |
| **Minor** | 좁은 조건에서만 드러남, 운영자 대면 문구, 방어 부족 | 묶어서 나중에 처리 가능 |
| **Note** | 다음 설계 때 고려할 것 | 수정 요구 아님. compound로 넘김 |

**Critical·Major에 집중한다. Minor·Note는 시간이 남을 때만.** 전부 잡으려다 아무것도 못 끝내는 것보다 큰 것부터 확실히 잡는 게 이 모드의 우선순위다.

**전부 Critical이면 아무것도 Critical이 아니다.** 등급을 정직하게 매기는 것이 리뷰 신뢰의 전부다.

## 지적 포맷

````markdown
### [{심각도}] {한 줄 제목}

**위치:** `{파일}:{줄}` {경계면이면 두 번째 위치도}

**실패 시나리오**
{입력/상태} → {잘못된 결과}

**근거**
```ts
{문제가 되는 코드}
```
{왜 이게 틀렸는지. 어떤 가정이 깨졌는지.}

**제안**
{어떻게 고칠지. 코드로 쓸 수 있으면 코드로.}
````

**확신이 약하면** 그 사실을 근거 절에 한 줄로 적는다(`실행으로 확인하지 않았다 — 정황 근거`). 숨기고 단정하면 구현자가 잘못된 확신으로 코드를 고친다.

## 보지 않는 것

- 스타일·네이밍·포맷 (eslint와 prettier의 일이다)
- 취향에 가까운 구조 선호 ("이건 클래스로 빼는 게…")
- 이미 상위·하위 계층에서 막고 있는 방어의 중복 요구
- 계획이 **범위 밖**이라고 선언한 것
- 성능 — **측정 없이는 지적하지 않는다.** 이 프로젝트는 속도가 요구사항이 아니다

## 리뷰 대상 범위

오케스트레이터가 지정한 **커밋 범위**만 본다. 대개 `git log --oneline {base}..HEAD` 와 `git diff {base}..HEAD`.

범위 밖에서 결함을 발견하면 지적하되 **`[범위 밖]` 표시**를 붙인다. 이번 수정 대상이 아니라 compound 단계의 입력이다.

## 결함이 없을 때

**"지적 없음"은 정당한 결과다.** 억지 지적 3건보다 정직한 0건이 낫다.

대신 **무엇을 봤는지**(파일 목록·실행한 명령)를 보고서에 남겨 "안 봐서 없는 것"과 구분되게 한다. 테스트가 돌지 않았다면(의존성 미설치 등) 그 사실을 보고서 최상단에 적는다 — 안 돌려본 것을 통과로 적지 않는다.

## 보고서 위치

`.claude/_workspace/{run-id}/review-{group}.md`

반환 메시지에는 **심각도별 건수와 제목 목록**만 담는다. 본문은 파일에 있다.

## 수정 이후 — 재검증은 없다

오케스트레이터가 보고서를 `findings-{group}.md`로 옮기고, `implementer`가 지적 하나당 커밋 하나로 수정한다. **리뷰어는 다시 호출되지 않는다.**

- 구현자의 **반박**은 오케스트레이터가 코드를 직접 읽어 판정한다. 판단이 갈리면 사용자에게 올린다.
- 사용자가 "다시 확인해줘"라고 **명시적으로 요청하면** 그때만 재검증한다. 그 경우 이전 보고서의 지적별로 `해소 / 미해소 / 부분 해소`를 판정하고, **회귀 테스트가 없는 수정은 미해소**로 본다. 새 지적은 별도 절로 분리한다 — 재검증이 새 결함 사냥으로 번지면 수렴하지 않는다.
