# 실행 계획 작성 규약

계획은 **구현자가 창작하지 않아도 되게 만드는 문서**다. 구현자가 창작하는 만큼 결과가 계획에서 벌어지고, 벌어진 만큼 리뷰가 판정 기준을 잃는다.

경로: `docs/plans/{YYYY-MM-DD}-{slug}.md` (`backend/` 기준)
전체 골격은 `references/plan-template.md`에 있다. 처음 쓸 때는 반드시 읽는다.

## 이 하네스에는 spec 문서가 없다

설계 결정을 **계획 문서 앞부분에 인라인한다.** 문서 두 개 사이의 승인 왕복과 동기화 비용을 없앤 구성이다. 대신 두 가지가 이 스킬의 책임이 된다.

**1. 설계 규율이 사라지지 않게 한다.** 계획 앞부분에 반드시 있어야 하는 것:

| 절 | 없으면 |
|---|---|
| **현행** (파일:줄로 특정) | 근거 없는 제안이 구현 단계에서 무너지고, 그 비용은 계획 재작성 전체다 |
| **결정** (버린 안과 이유 병기) | 반년 뒤에 근거 없이 뒤집힌다. 이 근거를 담을 다른 문서가 없다 |
| **에러 처리 표** | 구현자가 실패를 임의로 분류한다 — 외부 장애를 400으로 청구하는 오분류가 여기서 나온다 |
| **트레이드오프** | 포기한 것이 안 보이면 아직 충분히 보지 않은 것이다 |
| **범위 밖** | 구현이 무한히 번지고, 리뷰어가 "왜 이건 안 했나"를 지적으로 올린다 |

**2. 결정 공백을 임의로 메우지 않는다.** 설계가 갈리는 지점을 발견하면 **계획 작성을 멈추고 갈림길과 각 선택의 귀결만 반환한다.** 임의 판단은 코드가 되고, 잘못된 전제 위의 계획은 전부 폐기된다. spec 단계가 없다는 것은 사용자에게 물을 기회가 **계획 승인 게이트 한 번뿐**이라는 뜻이다 — 그 게이트에 질문을 올린다.

## 태스크 분할 기준

**하나의 태스크 = 하나의 커밋 = 그 시점에 테스트·타입 검사·린트 전부 통과.**

"Task 3까지 해야 컴파일된다"는 분할은 잘못됐다. 아래 순서를 지키면 대개 자연스럽게 독립된다.

1. 순수 함수·타입·DTO (의존 없음)
2. 엔티티·리포지토리 (스키마 → 조회 → 상태 변경)
3. 클라이언트·어댑터 (외부 서비스 래퍼)
4. 서비스 (위를 조합)
5. 컨트롤러·모듈 배선
6. 예외 필터·인터셉터 등 횡단 관심사

태스크가 15개를 넘으면 계획을 쪼개자고 제안한다.

## 다섯 Step을 지키는 이유

| Step | 없으면 |
|---|---|
| 실패 테스트 작성 | 구현 이후에 쓴 테스트는 구현을 그대로 베낀다 |
| **실패 확인** | 통과하는 이유가 구현 때문인지 테스트가 무력해서인지 구분 불가 |
| 구현 | — |
| 통과 확인 (**전체 테스트 + 타입 검사 + 린트**) | 방금 쓴 spec만 돌리면 회귀를 놓친다. 린트를 빼면 다음 태스크에서 뭉쳐 터진다 |
| 커밋 | 태스크가 뭉쳐 되돌릴 단위가 사라진다 |

**Expected 줄에 예상 실패 메시지를 구체적으로 적는다.** `Expected: FAIL`만으로는 구현자가 엉뚱한 이유의 실패를 통과로 오인한다.

## 코드 블록 작성 원칙

**삽입 위치를 특정한다.**
- 나쁨: "spec 파일에 테스트를 추가한다"
- 좋음: "`describe("ChatService", ...)` 블록 맨 끝(`classifyIntent` 테스트 다음)에 추가"

**전문을 쓴다.** `// ... 기존 코드 ...`로 얼버무리면 구현자가 그 부분을 창작한다. 기존 블록을 교체할 때는 교체 후 전문을 쓴다.

**새로 지어 쓰지 않는다.** 코드 예시는 커밋된 코드에서 가져온다. 새로 쓸 일이 생기면 **`backend/`에서 실제로 `npx eslint src --max-warnings=0`을 통과시킨 뒤** 그 형태를 옮긴다. backend는 eslint가 `recommendedTypeChecked`여서 관용적으로 보이는 테스트 코드가 error가 된다(`tb-tdd-implement/references/backend-constraints.md`의 typed-lint 절) — 컴파일되지 않는 예시는 구현자가 이탈을 만들어야 하고, 그 이탈이 매번 리뷰·판정 비용을 낸다.

**검증은 최종 상태가 아니라 태스크 경계마다 한다.** 게이트(`tsc` · `--max-warnings=0` 린트 · 전체 테스트)는 **태스크당 한 번씩 따로 돌기 때문**이다. 여러 태스크가 같은 파일을 키워갈 때 최종 상태 블록을 중간 태스크에 배치하면, 그 시점에 아직 쓰이지 않는 import·스파이·헬퍼가 `no-unused-vars`에 걸린다. 각 태스크 블록에는 **그 태스크의 테스트가 실제로 참조하는 것만** 넣고, 나머지는 처음 쓰이는 태스크에서 추가한다.

**계산이 필요한 기대값은 계산 근거를 남긴다.**
> 첫 테스트의 기대값: `must` 절은 지역 1 + 카테고리 2 = 3개.

### 코드 블록은 스냅샷이다 — 갱신할 때 다시 쓰지 않는다

작성 시점의 스냅샷이므로 **선행 태스크 실행·실행 중 확정된 규약**이 그것을 낡게 만든다.

- **완료·진행 중 태스크의 코드 블록을 다시 쓰지 않는다.** 원문을 그대로 두고 이후 사실을 바로 위에 blockquote로 병기한다.
  ```markdown
  > **[갱신 {날짜} — {무엇이 뒤집혔나}]** {근거}
  > **[구현 이탈 — `{해시}` {커밋 제목}]** {왜 블록대로 하지 않았나}
  ```
  **해시만 적지 않는다** — rebase·amend 후 존재하지 않는 커밋을 가리킨다. 커밋 제목이나 태스크 번호를 함께 적어 해시가 바뀌어도 추적되게 한다.
- 설계 결정을 정정했으면 **아래 태스크의 코드 블록에 역반영됐는지 같은 작업에서 확인한다.** 앞부분만 고치고 태스크를 그대로 두면 구현자가 옛 결정을 코드로 만든다 — spec을 없앤 구성에서 가장 쉽게 나는 사고다.
- 결정 정정이 **테스트 블록까지** 내려왔는지 센다. 구현 쪽만 반영되고 테스트 쪽이 빠지면 회귀 가드가 조용히 무력해진다.
- **기준은 계획 블록이 아니라 커밋된 코드다.** 이 문장을 계획의 Global Constraints에도 남긴다.

## Global Constraints

문서 앞에 모은다. 태스크마다 반복하지 않는다. backend에서 항상 들어가는 항목:

- 작업 디렉터리는 `backend/`. 모든 명령은 거기서 실행한다
- 언어 규약 (주석·로그·에러 메시지·커밋 메시지는 한국어)
- 테스트 `npm test` / 타입 검사 `npx tsc --noEmit -p tsconfig.json` / 린트 `npx eslint src --max-warnings=0`
- 테스트 파일은 소스 옆 `*.spec.ts` (jest `rootDir`가 `src`)
- 단위 테스트는 전부 모킹. 실제 네트워크·DB 호출을 하지 않는다
- 기준은 계획 블록이 아니라 커밋된 코드다
- {절대 하지 않을 것}

## 검증을 누가 실행하는가로 먼저 가른다

각 검증 항목을 쓰기 전에 **에이전트가 물리적으로 할 수 있는 일인지** 판단한다. 할 수 없는 것을 태스크 Step으로 넣으면 구현자는 건너뛸 수도 끝낼 수도 없어 **가능한 일부만 대체 확인하고 체크박스를 닫는다** — 그러면 아무도 보지 않은 경로가 다음 실행에서 "확인 완료"로 승계된다.

에이전트가 **못 하는 것**: 브라우저 조작 · 실제 외부 서비스 자격증명이 필요한 호출(Gemini·TEI·Qdrant 실서버) · 사내망 전용 자원(Postgres는 외부망에서 타임아웃).

- 그런 항목은 태스크에서 빼고 문서 끝의 **"사용자 확인 필요"** 절로 옮긴다. **체크박스를 두지 않는다** — 체크박스는 "에이전트가 닫을 수 있다"는 뜻이다.
- 항목마다 재현 절차와 **무엇이 보이면 통과인지**를 적는다. 사용자가 그것만 보고 실행할 수 있어야 한다.

## 꼬리 두 절은 오케스트레이터가 읽는 인터페이스다

계획 끝의 **`리뷰 묶음`과 `최종 검증`은 `tb-harness`가 파싱하는 입력**이다. 축약 실행에서도 빼지 않는다 — `최종 검증` 절이 없으면 오케스트레이터가 게이트를 임의로 구성해 대체하고, **계획만 아는 실측 항목**(env 없이 빌드 통과, 사용자 확인 필요 항목)이 조용히 검증에서 빠진다.

```markdown
## 리뷰 묶음

| 묶음 | 태스크 | 논리 단위 |
|---|---|---|
| A | 1~3 | DTO·검증 |
| B | 4~6 | 서비스 본체 |

## 최종 검증

- [ ] `npx tsc --noEmit -p tsconfig.json` 통과
- [ ] `npm test` 전체 통과
- [ ] `npx eslint src --max-warnings=0` 통과
- [ ] `npm run build` 성공
- [ ] {이 계획에서만 아는 실측 항목}
```

리뷰 묶음은 하나의 논리적 완결 단위로 **3~5개 태스크**를 묶는다. 전체를 다 만든 뒤 한 번에 리뷰하면 지적이 뭉쳐 나오고 되돌릴 거리가 멀어진다. **태스크가 5개 이하면 묶음 1개로 합친다** — 이 하네스의 review는 이미 경량이라 더 쪼갤 이득이 없다.

## 하지 말 것

- **완료된 태스크(`- [x]`)를 수정하지 않는다.** 재계획 시에도 마찬가지.
- **리뷰 지적을 뭉쳐 큰 태스크로 만들지 않는다.** 지적 하나당 태스크 하나 — 커밋이 뭉개진다.
- **결정 공백을 조용히 메우지 않는다.** 명시적으로 표시하고 반환 메시지의 미해결 질문에 올린다.
