# tb-harness — plan → work → review → compound

backend의 코드 변경이 지나가는 파이프라인. 이 스킬을 읽은 세션이 **오케스트레이터**다. 직접 구현하지 않는다 — 각 단계를 전문 에이전트에게 맡기고, 산출물을 잇고, 사용자 승인을 받는다.

**이 하네스의 세 가지 선택:**
1. **spec 문서가 없다.** 설계 결정을 계획 문서 앞부분에 인라인한다 — 문서 두 개 사이의 승인 왕복과 동기화 비용을 없앤다.
2. **review는 경량 단일 패스다.** 리뷰어 한 명이 정확성·계약·테스트품질을 한 번에 보고, 실행 기반 증명과 재검증을 생략한다.
3. **전 파이프라인을 태울지 사용자가 고른다.** 게이트 0에서 A(plan→work→review→compound)와 B(바로 구현)를 제시한다 — 작은 수정에 4단계를 강제하면 하네스를 우회하게 되고, 우회는 기록을 남기지 않는다.

셋 다 **속도를 위해 정확성을 일부 내놓은 절충**이며 사용자가 선택한 것이다. 임의로 되돌리지 않는다 — 되돌리고 싶으면 사용자에게 제안하고 답을 받는다.

## 실행 모드: 서브 에이전트

**이 환경에는 `TeamCreate`가 없다.** 에이전트 팀 모드는 쓸 수 없다. 조율은 다음 조합으로 한다.

| 수단 | 용도 |
|---|---|
| `Agent` 도구 | 단계별 전문 에이전트 호출. **모든 호출에 `model: "opus"`를 명시한다** |
| 반환값 | 에이전트 → 오케스트레이터 결과 수집 |
| 파일 (`.claude/_workspace/{run-id}/`) | 저널·리뷰 보고서·지적 목록 |
| `TaskCreate` / `TaskUpdate` | 태스크 진행 상황을 사용자에게 노출 |
| `SendMessage` | 이미 띄운 명명 에이전트를 컨텍스트 유지한 채 재호출 |

`subagent_type`에는 `.claude/agents/`의 이름을 넣는다(`plan-writer` · `implementer` · `reviewer` · `compounder`). 이름이 해석되지 않으면 `"general-purpose"`로 띄우고 **프롬프트 첫 줄에 `.claude/agents/{name}.md`를 먼저 읽으라**고 지시한다.

**모든 명령은 `backend/`에서 실행된다.** 경로는 전부 `backend/` 기준이다.

### 모델

전원 `opus`. 이 하네스의 품질은 에이전트의 추론에 직결된다.

**속도가 더 필요하면 `implementer`만 `sonnet`으로 내린다** — 계획이 시그니처까지 정해준 상태의 코드 작성이라 판단 부담이 가장 작은 단계다. 사용자가 요청할 때만 내리고, 저널에 기록한다. 계획이 판단을 요구하는 상태로 넘어왔다면 그건 모델을 올릴 이유가 아니라 **계획의 결함**이다.

## 다른 스킬과의 관계

| 상황 | 사용 |
|---|---|
| backend 코드 변경 (기본) | **`tb-harness`** — 저장소 규약·워크스페이스 제약·누적 학습을 아는 것은 이쪽뿐이다 |
| 사용자가 `/ce-plan`·`/superpowers:*`를 **직접 호출** | 사용자 지시가 우선. 그대로 따른다 |
| 요구사항 자체가 불명확해 발산이 필요 | Phase 1 앞에 `superpowers:brainstorming`을 붙이고, 결론을 `plan-writer`의 입력으로 넘긴다 |
| **버그인데 원인을 모른다** (에러 메시지·스택트레이스만 있음) | 먼저 `superpowers:systematic-debugging`으로 근본 원인을 찾고, **그 원인을 요구사항으로** Phase 1에 넘긴다. 원인 없이 세운 계획은 증상만 덮는다 |
| `core`·`frontend`만 건드리는 작업 | 이 하네스는 backend 전용이다. 경계면 짝(`backend-constraints.md`의 경계 표)에 걸릴 때만 함께 다룬다 |

## Phase 0: 컨텍스트 확인 — 항상 먼저

`.claude/_workspace/`를 확인해 실행 모드를 정한다.

| 상황 | 모드 | 행동 |
|---|---|---|
| 해당 작업의 `_workspace/{run-id}/`가 없음 | **초기 실행** | **게이트 0**부터 |
| `_workspace/{run-id}/` 있음 + 부분 수정 요청 | **부분 재실행** | 해당 Phase만 (아래 매트릭스). 게이트 0 없음 |
| `_workspace/{run-id}/` 있음 + 새 요구사항 | **새 실행** | 기존을 `_workspace/{run-id}_prev/`로 옮기고 **게이트 0**부터 |
| 계획에 미완료 체크박스가 남음 | **이어서 실행** | 남은 태스크 묶음부터 Phase 2 |
| 계획은 있는데 커밋이 없음 + 사용자가 "진행"/"이어서" | **게이트 1 통과 처리** | Phase 1을 다시 돌리지 않는다. Phase 2부터 |

**부분 재실행 매트릭스**

| 요청 | 실행할 Phase |
|---|---|
| "설계 다시" / "계획 고쳐줘" / "계획만 수정" | 1 |
| "리뷰만 다시" | 3 |
| "지적 고쳐줘" | 3의 수정 루프 |
| "학습 정리해줘" | 4 |

**run-id**는 `{YYYY-MM-DD}-{slug}`. slug는 계획 파일명과 동일하게 맞춘다.

작업 디렉터리를 만든다: `.claude/_workspace/{run-id}/` — `journal.md`를 여기에 append한다.

### 재개할 때는 저널만 읽지 않는다

**`ls .claude/_workspace/{run-id}/` 와 `git log`·`git status`·`git diff`를 먼저 보고 저널과 대조한다.** 저널은 단계가 끝날 때 쓰이므로 세션이 중간에 끊기면 실제 상태보다 낡는다. 어긋나면 **파일·git이 맞고 저널이 틀린 것이다** — 저널을 먼저 정정하고 나서 재개 지점을 정한다.

| 실제 상태 | 저널이 이렇게 말해도 | 판정 |
|---|---|---|
| `review-{group}.md`가 있다 | "리뷰: 아직 안 함" | 리뷰는 돌았다. **지적이 처리되지 않은 채 방치된 것이다** |
| `findings-{group}.md`가 있는데 수정 커밋이 없다 | "처리: 수정 n건" | 수정 루프가 안 돌았다. 여기가 재개 지점이다 |
| 계획 체크박스 `[x]`인데 해당 커밋이 없다 | — | rebase로 해시가 바뀌었을 수 있다. 커밋 제목으로 다시 찾는다 |
| 계획 커밋 뒤에 커밋이 있다 | "코드 변경 없음" | 태스크가 진행됐다. **저널을 믿고 다시 구현하면 중복 작업이다** |
| `git status`가 더럽다 | 아무 말 없음 | 아래 분류를 거치기 전까지 재개하지 않는다 |

**미커밋 소스 변경은 hunk 단위로 계획과 대조해 분류한다.** 두 종류가 겉모습이 같아서, 분류 없이 이어가면 어느 쪽이든 한 번에 잘못 확정된다.

| 근거 | 조치 |
|---|---|
| 계획의 어느 태스크 블록과 일치 | **진행분.** 검증(테스트·타입 검사·린트)을 처음부터 돌린 뒤 그 태스크로 커밋한다 — 중단된 세션이 검증까지 갔다는 증거는 없다 |
| 계획에도 HEAD에도 근거 없음 | **원복하고 저널에 남긴다.** 원인을 못 찾아도 "원인 불명이라 유지"는 선택지가 아니다 |

근거 없는 변경을 그대로 커밋하는 것이 위험한 이유: 분기별 실제 응답이 아직 없는 코드에서는 두 핸들러 호출이 뒤바뀌어도 **테스트가 전부 초록불이다.** 검증으로는 잡히지 않는다.

## 게이트 0 — 경로 선택 (초기 실행·새 실행일 때만)

Phase 0이 **초기 실행** 또는 **새 실행**으로 판정했으면, Phase 1로 가기 전에 사용자가 경로를 고른다. `AskUserQuestion` 하나로 묻는다.

**부분 재실행·이어서 실행·게이트 1 통과 처리는 이 게이트를 건너뛴다** — 경로는 그 실행이 시작될 때 이미 정해졌다. 후속 요청마다 다시 물으면 같은 질문이 반복되고, 진행 중인 실행의 절반이 다른 경로로 갈린다.

| 경로 | 무엇이 도는가 | 산출물 |
|---|---|---|
| **A. 전체 하네스** | Phase 1 → 2 → 3 → 4 (plan → work → review → compound) | 계획 문서 · 커밋 · 리뷰 보고서 · 학습 |
| **B. 바로 구현** | `implementer` 하나 → 검증 3종 → 커밋 | 커밋 · `quick-log.md` 한 줄 |

**B는 plan·review·compound를 전부 생략한다.** 남는 안전망은 검증 3종(`npm test` · `npx tsc --noEmit -p tsconfig.json` · `npx eslint src --max-warnings=0`)과 구현자의 TDD 규약뿐이다. 사용자가 그 절충을 명시적으로 고른 것이므로 **리뷰를 몰래 끼워 넣지 않는다** — 안전하게 만들려고 고르지 않은 단계를 추가하면 사용자가 무엇을 받게 될지 예측할 수 없다.

**추천을 붙여서 묻는다.** 사용자가 뒤집을 수 있지만 판단 근거는 제시한다.

| 이런 변경이면 | 추천 | 왜 |
|---|---|---|
| 새 파일·새 모듈·외부 연동(DB·API·큐) 추가 | **A** | 되돌릴 거리가 멀고 설계 결정이 남는다 |
| DTO·응답 계약·마이그레이션 변경 | **A** | 경계면 짝이 있고 타입 시스템이 그 짝을 연결해주지 않는다 |
| 에러 처리 분기·폴백 경로 신설 | **A** | 조용히 실패하는 종류다. 응답이 200이고 화면도 정상이라 관측이 로그 한 줄에 걸린다(`test-asymmetry`) |
| 기존 파일 국소 수정 · 문구·상수 변경 | **B** | |
| 테스트만 추가 · 주석 정리 | **B** | |
| 리뷰가 이미 지적한 것을 고치는 후속 | 게이트 없음 | 진행 중인 실행의 수정 루프다 |

### B 경로 실행 절차

1. **`implementer`를 띄운다. 오케스트레이터가 직접 짜지 않는다.** TDD 규약과 워크스페이스 제약(`backend-constraints.md`)을 아는 것은 구현자이고, 컨텍스트도 그쪽이 싸다. B에서 절약하는 것은 계획·리뷰·학습이지 구현 품질이 아니다.
2. `_workspace/{run-id}/`를 만들지 않는다. 대신 `.claude/_workspace/quick-log.md`에 **한 줄** append한다:
   `- {YYYY-MM-DD} {커밋 해시} {요청 한 줄 요약} — {변경 파일 수}개 파일`
   이 한 줄이 다음 A 경로 실행에서 `compounder`의 입력이 된다. **B가 남발되면 여기에 같은 성질의 수정이 쌓이고, 그 자체가 "계획이 필요했다"는 증거가 된다.** 한 줄의 비용으로 복리를 끊지 않는다.
3. **검증 3종이 실패하면 커밋하지 않고 사용자에게 보고한다.** B에는 리뷰가 없으므로 여기서 넘기면 아무도 잡지 않는다.
4. 구현자가 "계획이 필요하다"·"설계 결정이 필요하다"고 보고하면 **A로 승격한다.** 사용자에게 알리고 Phase 1부터 시작한다 — B에서 억지로 밀지 않는다. 승격은 실패가 아니라 게이트가 제 역할을 한 것이다.

## Phase 1: plan

**실행 모드:** 서브 에이전트 1회. spec 단계가 없으므로 `plan-writer` 하나가 조사·설계 결정·태스크 분해를 모두 한다.

```
Agent({
  subagent_type: "plan-writer",
  model: "opus",
  name: "plan-writer",
  run_in_background: false,
  prompt: `요구사항: {사용자 요청 원문}

run-id: {run-id}

.claude/learnings/ 전체와
.claude/skills/tb-tdd-implement/references/backend-constraints.md 를 먼저 읽어라.

docs/plans/{run-id}.md 를 작성하라. 이 하네스에는 spec 문서가 없다 —
현행(파일:줄로 특정) · 결정(버린 안 병기) · 에러 처리 표 · 트레이드오프 ·
범위 밖을 문서 앞부분에 인라인하고, 그 뒤에 TDD 태스크를 전개하라.

문서 경로 · 핵심 설계 결정 · 태스크 목록 · 리뷰 묶음 경계 ·
미해결 질문을 반환하라.`
})
```

**미해결 질문이 반환되면 사용자에게 묻는다.** 임의로 정하고 진행하지 않는다 — spec 단계가 없어서 사용자에게 물을 기회는 게이트 1 한 번뿐이다. 잘못된 전제 위의 계획은 전부 폐기된다.

### 게이트 1 — 계획 승인 (Phase 1의 하드 정지점)

**여기서 반드시 멈춘다.** 설계 결정과 태스크가 한 문서에 있으므로, 이 승인 하나가 이전 하네스의 spec 승인 + 계획 승인을 겸한다.

사용자에게 다음을 제시한다:

```
## Phase 1 완료 — 승인 요청

**계획:** docs/plans/{run-id}.md

**핵심 설계 결정**
- {결정과 버린 안 3~5줄}

**태스크** {n}개 / 리뷰 묶음 {m}개
- 묶음 A: Task 1~{k} — {요약}
- 묶음 B: Task {k+1}~{n} — {요약}

**트레이드오프:** {계획이 명시한 것}
**범위 밖:** {계획이 명시한 것}

[미해결 질문이 있으면] 다음을 결정해 주세요: {질문 목록}

승인하시면 구현에 들어갑니다.
```

**사용자 응답 없이 Phase 2를 시작하지 않는다.**

| 사용자 응답 | 행동 |
|---|---|
| "진행" / 승인 | Phase 2 시작 |
| 계획 수정 요청 | Phase 1로 되돌린다. 수정 후 이 게이트를 다시 통과한다 |
| 미해결 질문에 답변 | 답을 `plan-writer`에 전달해 계획을 갱신하고, 이 게이트를 다시 통과한다 |
| "구현은 sonnet으로" | `implementer`를 `model: "sonnet"`으로 띄운다. 저널에 기록 |

승인되면 오케스트레이터가 두 가지를 한다:

1. **계획 문서를 커밋한다** — `docs(backend): {run-id} 구현 계획을 작성한다`. 이 커밋이 첫 묶음의 리뷰 `base`가 되므로, 여기서 커밋해두면 리뷰 범위가 코드 변경과 정확히 일치한다. 계획을 나중에 커밋하면 계획 diff가 리뷰 범위에 섞인다.
2. 태스크 목록을 `TaskCreate`로 등록해 진행 상황이 보이게 한다.

`journal.md`에 기록: 계획 경로 · 계획 커밋 해시 · 핵심 결정 · 태스크 수 · 리뷰 묶음 · 사용자가 답한 미해결 질문 · implementer 모델.

## Phase 2 ⇄ Phase 3: work / review 증분 루프

```
묶음 A: work → review → 정리 → 수정 → 묶음 B: work → review → ... → 최종 검증 → Phase 4
```

**전체를 다 만든 뒤 한 번에 리뷰하지 않는다.** 지적이 뭉쳐 나오고 되돌릴 거리가 멀어진다. 계획이 제안한 **리뷰 묶음마다** Phase 3을 돈다. (태스크 5개 이하면 계획이 묶음 1개로 합쳐 놓았을 것이다)

### Phase 2: work — implementer

묶음 하나당 `implementer` 하나. 컨텍스트 격리를 위해 **묶음마다 새 에이전트**를 띄운다.

**게이트 1을 통과했는지 먼저 확인한다.** 사용자 승인 없이 이 Phase를 시작하지 않는다.

```
Agent({
  subagent_type: "implementer",
  model: "opus",           // 사용자가 요청했으면 "sonnet"
  name: "implementer-{group}",
  run_in_background: false,
  prompt: `계획: docs/plans/{run-id}.md
담당 태스크: Task {n}~{m} (리뷰 묶음 {group})
run-id: {run-id}

.claude/learnings/ 를 먼저 읽어라.
태스크당 다섯 Step(실패 테스트→실패 확인→구현→통과 확인→커밋)을 지키고,
태스크당 커밋 하나를 만들어라.
통과 확인은 npm test + npx tsc --noEmit -p tsconfig.json +
npx eslint src --max-warnings=0 셋 다다.
계획을 벗어나야 하는 상황이면 임의로 고치지 말고 멈추고 보고하라.
커밋 목록·계획 이탈·검증 결과·발견 사항을 반환하라.`
})
```

**계획 이탈이 보고되면 멈춘다.** 오케스트레이터가 판단한다:
- 계획이 틀렸다 → `plan-writer`를 재호출해 해당 태스크만 고친다. 계획이 바뀌면 **게이트 1을 다시 통과한다**
- 설계 결정이 틀렸다 → 같이 `plan-writer`로 되돌린다. 앞부분 결정을 고치면 **아래 태스크 블록에 역반영됐는지 확인한다**
- 사소한 차이다 → 이탈을 저널에 기록하고 진행 (리뷰어가 이 기록을 본다)

**묶음 시작 커밋 해시(`base`)를 기록해둔다.** 리뷰 범위가 된다. 첫 묶음의 `base`는 게이트 1에서 만든 계획 커밋이고, 이후 묶음의 `base`는 앞 묶음의 마지막 커밋(수정 커밋 포함)이다.

### Phase 3: review — reviewer 단일 패스

**`Agent` 호출 하나면 된다.** 정확성·계약·테스트품질을 한 패스에서 함께 본다.

```
Agent({
  subagent_type: "reviewer",
  model: "opus",
  run_in_background: false,
  prompt: `리뷰 대상: git diff {base}..HEAD  (리뷰 묶음 {group}, Task {n}~{m})
계획: docs/plans/{run-id}.md
구현자가 보고한 계획 이탈: {있으면 그대로 전달}
run-id: {run-id}

.claude/learnings/ 를 먼저 읽어라.
경계면 교차 비교(양쪽 파일을 동시에 열고 대조) → 계획 이탈 →
정확성 → 테스트 품질 순으로 본다.
모든 지적에 실패 시나리오를 붙여라 — 못 만들면 그 지적은 버려라.
Critical·Major를 우선한다. 시간이 부족하면 Minor·Note는 생략해도 된다.
보고서를 .claude/_workspace/{run-id}/review-{group}.md 에 쓰고,
심각도별 건수와 제목 목록을 반환하라.`
})
```

**고위험 변경(인증·삭제·마이그레이션)이면 이 모드로 충분한지 사용자에게 물어본다.** 자동으로 강도를 올리지 않는다 — 이 하네스에 다른 리뷰 모드는 없으므로, 필요하면 사용자가 수동 검토를 넣을지 결정해야 한다.

### 3-1. 정리 — 오케스트레이터가 직접 한다

**`review-{group}.md`가 생긴 직후 저널을 append한다.** 단계가 끝날 때까지 미루지 않는다 — 여기서 세션이 끊기면 다음 세션이 리뷰를 미실행으로 오판하고 지적이 방치된다.

`review-{group}.md`를 읽고 `.claude/_workspace/{run-id}/findings-{group}.md`로 옮긴다. 리뷰어가 하나라 교차 병합은 없다 — `[범위 밖]` 표시된 지적만 수정 대상에서 빼서 Phase 4 입력으로 남긴다.

**게이트 2 (Critical이 있을 때만):** Critical 지적은 사용자에게 보고하고 수정 방향을 확인받는다. Major 이하는 바로 수정 루프로 넘어간다.

### 3-2. 수정 — implementer 재호출

같은 묶음의 `implementer-{group}`을 `SendMessage`로 재호출한다(컨텍스트가 살아 있어 맥락 설명이 필요 없다). 죽었으면 새로 띄운다.

```
지적 목록: .claude/_workspace/{run-id}/findings-{group}.md
지적 하나당 커밋 하나. 지적을 재현하는 테스트를 먼저 추가하라.
동의하지 않는 지적은 고치지 말고 반박 근거와 함께 반환하라.
지적별로 수정함/반박/보류를 빠짐없이 명시하라.
```

**`findings-{group}.md`를 만들었으면 그 실행 안에서 수정 루프를 닫는다.** 못 닫으면(사용자가 멈췄거나, 상위 결정이 필요하거나, 다음 묶음으로 이월하기로 했다면) 저널에 **`미해결 이월: {n}건 — {findings 파일}의 {지적 제목}`**을 명시적으로 남기고 사용자 보고에도 올린다. 지적을 만들어 놓고 저널이 침묵하면 그 지적은 사라진다.

수정이 끝나면 `findings-{group}.md`의 해당 지적에 `[해소 — {커밋 해시} {커밋 제목}]`을 덧붙인다. 해시만 적으면 rebase 후 끊긴다.

### 3-3. 재검증 — 하지 않는다

**이게 review 경량화의 핵심 트레이드오프다.** 수정이 실제로 지적을 해소했는지 아무도 다시 확인하지 않는다. `implementer`의 수정 보고를 그대로 신뢰한다.

- **반박이 올라오면 오케스트레이터가 코드를 직접 읽고 판정한다**(리뷰어를 다시 부르지 않는다). 판단이 갈리면 사용자에게 올린다.
- 사용자가 "다시 확인해줘"/"재검증해줘"라고 **명시적으로 요청하면** 그때만 `reviewer`를 재호출한다. **최대 1회** — 그래도 수렴 안 되면 설계 문제로 보고 사용자에게 올린다.
- 다만 **회귀 테스트 유무는 오케스트레이터가 `git show`로 직접 확인한다.** 수정 커밋에 테스트가 없으면 구현자에게 다시 요구한다 — 이건 재검증이 아니라 값싼 확인이다.

각 묶음이 끝날 때 `journal.md`에 append: 묶음 · 커밋 범위 · 지적 건수(심각도별) · 수정/반박/보류 내역 · 미해결 이월.

## Phase 4: compound

모든 묶음이 끝나고 **최종 검증**(계획의 "최종 검증" 절)이 통과한 뒤에 실행한다.

```
Agent({
  subagent_type: "compounder",
  model: "opus",
  run_in_background: false,
  prompt: `run-id: {run-id}

입력:
- .claude/_workspace/{run-id}/journal.md
- .claude/_workspace/{run-id}/findings-*.md
- .claude/_workspace/quick-log.md (있으면) — 지난 A 실행 이후 B 경로로
  처리된 수정 목록이다. 같은 성질의 수정이 반복돼 있으면 그것이
  "계획이 필요했다"는 증거다. 반복 패턴이 보이면 학습 후보로 올려라.
  읽고 나면 반영한 구간까지 처리 표시를 남겨라 — 다음 실행이 같은 줄을 다시 세지 않는다.
- .claude/learnings/ 전체
- docs/plans/{run-id}.md
- git log {첫 커밋}..HEAD

이 하네스의 review는 실행 증명과 재검증을 생략한다 —
"지적 없음"이 결함 없음의 증거가 아니라는 전제로 읽어라.
수정 커밋에 회귀 테스트가 붙었는지 git log로 직접 확인하라.

일반화 가능한 것만 학습으로 남겨라. 없으면 없다고 하라.
같은 성질의 지적이 2회 이상이면 스킬·에이전트 정의를 고치고
CLAUDE.md 변경 이력에 기록하라.
정책·취향·워크플로 단계 변경은 직접 고치지 말고 제안으로 반환하라.
신규 학습·승급 내역·삭제한 학습·사용자 판단 필요 항목을 반환하라.`
})
```

**게이트 3:** 하네스 파일(`.claude/skills/`, `.claude/agents/`, `CLAUDE.md`)이 수정됐으면 **무엇을 왜 고쳤는지 사용자에게 보고**한다. 하네스가 조용히 바뀌면 다음 실행의 동작을 예측할 수 없다.

보고 후 오케스트레이터가 커밋한다 — 학습 파일은 `chore(harness): {run-id}에서 얻은 학습을 반영한다`, 하네스 수정이 함께 있으면 **커밋을 나눈다**(학습 축적과 규칙 승급은 되돌릴 단위가 다르다).

### 마지막에 피드백을 청한다

강요하지 않되 반드시 기회를 준다:

> 결과에서 개선할 부분이 있나요? 에이전트 구성이나 단계 순서에 바꾸고 싶은 점이 있나요?

| 피드백 | 대상 |
|---|---|
| 산출물 품질 | 해당 단계의 스킬 |
| 에이전트가 놓친 관점 | 해당 에이전트 정의 |
| 단계 순서·승인 지점 | 이 파일 (`tb-harness`) |
| 트리거가 안 걸림 | 해당 스킬 description |

## 데이터 전달

```
backend/.claude/_workspace/
├── quick-log.md            # B 경로 전용. 실행당 한 줄. 다음 A 실행의 compounder가 읽는다
└── {run-id}/               # A 경로만 만든다
    ├── journal.md          # 전 단계 append. Phase 4의 주 입력
    ├── review-{group}.md   # reviewer 보고서
    └── findings-{group}.md # 오케스트레이터가 정리

backend/docs/plans/{run-id}.md    # 사용자 자산 — 커밋한다
backend/.claude/learnings/*.md    # 복리 자산 — 커밋한다
```

`_workspace/`는 gitignore 대상이지만 **삭제하지 않는다.** 사후 검증과 다음 compound의 입력이다.

`quick-log.md`는 run-id 디렉터리 **밖**에 둔다 — B 경로에는 run-id가 없고, 이 파일은 여러 B 실행에 걸쳐 누적돼야 패턴이 보인다.

### journal.md 포맷

```markdown
# {run-id}

## Phase 1 — plan
- plan: {경로} (태스크 {n}개, 묶음 {m}개)
- 핵심 결정: {요약}
- 사용자 결정: {미해결 질문에 답한 내용}
- 게이트 1: 승인 {날짜/시각}
- implementer 모델: {opus | sonnet}

## 묶음 {group} — Task {n}~{m}
- 커밋: {base}..{head} ({k}건)
- 계획 이탈: {내용 또는 없음}
- 리뷰: Critical {a} / Major {b} / Minor {c} / Note {d} — 보고서: review-{group}.md
- 처리: 수정 {x} / 반박 {y} / 보류 {z}
- 회귀 테스트 확인: {수정 커밋 n건 중 m건에 테스트 있음}
- 미해결 이월: {없음 | {n}건 — {지적 제목}, 어디로 이월했는지}
- 재검증: {없음(기본) | 1회(사용자 요청)}

## 최종 검증
- {명령} → {결과}
```

## 에러 핸들링

| 상황 | 대응 |
|---|---|
| 에이전트가 결과 없이 실패 | **1회 재시도.** 재실패면 그 단계 산출물 없이 진행하고 **저널과 사용자 보고에 누락을 명시**한다 |
| 구현자가 3회 시도해도 막힘 | 중단. 지금까지의 커밋과 막힌 지점을 사용자에게 보고 |
| 계획 이탈이 설계 결정 수준 | Phase 1로 되돌린다. 우회 구현을 승인하지 않는다. 결정 정정이 태스크 블록에 역반영됐는지 확인한다 |
| 게이트 1에서 사용자가 응답하지 않음 | **기다린다.** "승인으로 간주"하고 Phase 2를 시작하지 않는다 |
| 리뷰 지적과 구현자 반박이 정면 충돌 | 오케스트레이터가 코드를 직접 읽고 판정. 갈리면 양쪽 병기 + 출처 표기 후 사용자 판단 |
| 사용자 요청으로 재검증했는데도 수렴 안 됨(2회차) | 멈추고 사용자에게 올린다 (설계 문제일 가능성) |
| 최종 검증 실패 | Phase 4로 넘어가지 않는다. 실패를 보고하고 수정 루프로 되돌린다 |
| `_workspace/` 쓰기 실패 | 저널 없이 진행하지 않는다 — Phase 4의 입력이 사라진다. 경로를 확인하고 중단 |
| `_workspace/`가 유실된 상태로 재개 | git log·계획 체크박스·커밋 메시지로 저널을 역복원하고 **머리말에 "재구성본"임과 무엇이 소실됐는지 명시**한다. 지적 원문은 복원 불가이므로 Phase 4가 그 한계를 전제하게 한다 |
| 저널과 `_workspace/` 파일이 어긋남 | **파일이 기준이다.** 저널을 먼저 정정하고 재개 지점을 다시 정한다 (Phase 0의 대조 표) |

**보고는 정직하게 한다.** 건너뛴 단계, 실패한 검증, 누락된 지적은 전부 사용자에게 말한다.

## 하지 않는 것

- **오케스트레이터가 직접 구현하지 않는다.** 급해 보여도 `implementer`를 띄운다. 직접 짜면 리뷰 대상이 없어지고 저널이 비어 compound가 굶는다.
- **게이트를 건너뛰지 않는다.** 게이트 0(경로 선택)과 게이트 1(계획 승인) 모두 사용자 응답 없이 다음으로 가지 않는다. **경로를 오케스트레이터가 대신 고르지 않는다** — "이건 작아 보이니까 B로 하겠다"는 판단이 게이트를 없앤다.
- **A 경로에서 계획 없이 구현하지 않는다.** 리뷰가 기준을 가지려면 계획이 있어야 한다. 계획을 빼고 싶으면 게이트 0에서 B를 고른다 — A를 골라 놓고 계획만 빼는 것은 리뷰어에게 판정 기준 없이 판정하라는 뜻이다.
- **A 경로에서 review를 임의로 생략하지 않는다.** 이미 경량화됐으므로 더 줄일 것이 없다. B의 생략은 **사용자가 게이트 0에서 명시적으로 고른 것**이고, 오케스트레이터가 A 안에서 판단으로 빼는 것과 다르다.
- **B 경로에 단계를 몰래 더하지 않는다.** 안전해 보이게 만들려고 리뷰를 끼워 넣으면, 사용자가 고른 것과 받는 것이 달라진다. 더 필요하다고 판단되면 **말하고 승격한다**(B 경로 실행 절차 4).

## 규모에 맞춘 축약

| 규모 | 축약 |
|---|---|
| 태스크 3개 이하 | 리뷰 묶음 1개로 합친다. 설계 결정 절은 유지 — 짧게 쓰되 빼지 않는다 |
| 버그 수정 1건 | Phase 1을 "재현 테스트 + 수정 태스크" 계획 하나로. review는 그대로 돈다 |
| `core`·`frontend` 경계에 걸치는 변경 | `reviewer` 프롬프트에 **경계면 교차 비교를 특히 강조**하도록 명시한다. 타입 시스템이 이 짝을 연결해주지 않는다 |
| 리팩터링 (동작 무변경) | `reviewer`에게 테스트 품질(회귀 공백) 비중을 높이라고 명시한다. 최종 검증(기존 테스트 전부 통과)이 동작 보존의 유일한 증거다 |

**A 경로에서 compound는 항상 유지한다** — 이번 실행에서 잡힌 것을 다음 실행의 규칙으로 남기는 유일한 단계다. 위 축약은 전부 A 안에서의 조정이고, 파이프라인 자체를 줄이는 결정은 게이트 0에 있다.

**B 경로는 compound를 생략하지만 복리가 끊기지는 않는다** — `quick-log.md` 한 줄이 최소한의 자리를 메우고, 다음 A 실행의 `compounder`가 그 로그를 읽는다.
