# review의 "실행 증명 생략"은 reviewer에게만 걸린 제약이다 — 구현자의 자체 뮤테이션까지 금지한 것이 아니다

**증상**
`tb-code-review`가 포기 목록에 "실행 기반 증명(임시 테스트 작성, 구현 뮤테이션)"과 "재검증 사이클"을 올려 두었다. 이 문장을 **파이프라인 전체의 금지**로 읽으면, 리뷰 지적을 테스트 추가로 고친 구현자도 그 테스트의 검출력을 확인하지 않고 커밋한다. 이 하네스에는 재검증이 없으므로 그대로 닫힌다.

**결과**
"테스트를 추가했다"가 "그 테스트가 결함을 잡는다"의 증거가 되지 않는다. 지적이 요구한 경로를 실제로 덮었는지 **아무도 모르는 채로** 해소 처리된다. 리뷰가 이미 확신을 낮춘 모드인데, 수정 쪽에서도 확신을 낮추면 방어선이 두 겹 다 얇아진다.

**대응**
리뷰 지적을 테스트 추가로 해소할 때, 구현자는 **지적의 실패 시나리오를 임시로 주입해 새 테스트가 red가 되는 것을 확인하고 원복한다.** 비용은 지적당 수 분이고, 이 하네스가 가장 약한 지점을 정확히 메운다.

- 새 테스트 **하나만** 빨간불이 되는지 본다. 여러 개가 함께 터지면 시나리오를 잘못 주입한 것이다.
- 뮤테이션은 **커밋에 포함되지 않는다.** `git diff --stat`이 비는 것으로 원복을 증명한다.
- 오케스트레이터는 원복을 `git status`로 재확인한다 — 구현자의 보고만 받지 않는다.

2026-07-29 실행에서 구현자가 요청 없이 이것을 했고 지적 2건 모두 검출력이 확인됐다. 폴백 분기(`if (query.fellBackToRawMessage) return { reply: query.queryText, ... }`)를 임시로 넣자 새 테스트 하나만 red가 됐고, `CONDITION_LABELS.region`을 `'지역:'`→`'시도:'`로 바꾸자 지적이 예언한 시나리오가 그대로 재현됐다.
