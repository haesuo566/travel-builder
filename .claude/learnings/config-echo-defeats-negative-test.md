# 라이브러리가 설정값을 그대로 에코하는 형태로 넘기면 "비허용 입력에는 아무 일도 없다"를 테스트할 수 없다

**증상**
같은 옵션이 **넘긴 값의 형태(타입)에 따라 다른 코드 경로**를 타는 라이브러리에, 가장 단순한 형태로 값을 넘긴다. 단순한 형태에서는 라이브러리가 입력을 **검사하지 않고 설정값을 그대로 응답에 되돌려준다.**

실제 예: `cors@2.8.6`의 `configureOrigin`(`node_modules/cors/lib/index.js`)은 `origin`이 문자열이면 요청 `Origin`과 **무관하게** `Access-Control-Allow-Origin: <설정값>`을 항상 붙인다. 배열이면 `isOriginAllowed`를 거쳐 불일치 시 헤더를 아예 빼놓는다.

**결과**
보안 결과는 같아 보여도(브라우저가 결국 차단) **부정 케이스 테스트가 성립하지 않는다.** "허용되지 않은 origin에는 헤더가 붙지 않는다"를 고정할 수 없으므로, 누군가 나중에 `origin: true`(와일드카드)로 되돌려도 초록불이다. 허용 케이스만 있는 테스트는 화이트리스트가 실제로 화이트리스트로 동작하는지 아무것도 증명하지 않는다.

**대응**
- 화이트리스트·필터·매칭 성격의 설정은 **라이브러리가 실제로 매칭을 수행하는 형태**로 넘긴다(단일 값이라도 배열·판정 함수). 값이 하나뿐이라는 이유로 스칼라를 고르지 않는다.
- 형태별 분기는 **문서나 기억이 아니라 `node_modules/<pkg>` 소스를 읽어 확인한다.** 두 형태의 관측 가능한 차이(헤더가 붙는지/빠지는지)를 표로 적고 그 위에 테스트를 설계한다.
- 부정 단정을 쓸 때는 **그 단정이 실제로 빨간불이 될 수 있는지** 뮤테이션으로 한 번 확인한다(배열→문자열로 되돌려 부정 케이스가 깨지는지). 실효 없는 부정 단정 일반론은 `negative-assertions-resist-mutation.md` 참조.
