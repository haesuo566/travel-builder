# 학습 축적·하네스 갱신 규약

이번 실행에서 태운 시간을 다음 실행의 속도로 바꾼다. 그게 전부다.

**핵심 긴장:** 학습을 많이 남길수록 다음 실행의 컨텍스트가 무거워진다. 축적은 **늘리기가 아니라 정확도 유지**다. 남길 값어치가 없는 것을 남기면 값어치 있는 것이 묻힌다.

## 무엇이 학습인가

**남긴다** — 다음에 같은 상황에서 **판단을 바꿀 것**:
- 반복된 결함 유형 (예: 실패의 책임을 잘못된 대상에게 청구)
- 이 코드베이스 고유의 함정 (예: `CREATE TABLE IF NOT EXISTS`는 기존 테이블에 no-op)
- 도구·환경의 제약 (예: 이 환경에는 `TeamCreate`가 없어 에이전트 팀을 못 쓴다)
- 계획이 반복적으로 놓치는 항목
- 사용자가 두 번 이상 같은 방향으로 되돌린 선택

**남기지 않는다** — 컨텍스트만 좀먹는 것:
- 이번 한 번의 오타·단순 실수
- 코드를 읽으면 알 수 있는 사실 (구조, 함수 목록, 디렉터리)
- git 이력이 이미 기록한 것 ("무엇을 고쳤다")
- 특정 태스크에만 해당해 일반화 불가능한 세부
- 이미 스킬 본문에 있는 규칙의 재진술

## 학습 파일 포맷

`.claude/learnings/{kebab-slug}.md`

```markdown
---
type: pitfall | convention | environment | process
first_seen: {YYYY-MM-DD}
occurrences: {n}
promoted_to: {승급한 파일 경로 또는 없음}
---

# {한 줄 제목 — 무엇을 조심해야 하는가}

**증상**
{어떤 코드·상황에서 나타나는가}

**결과**
{그대로 두면 실제로 무슨 일이 일어나는가}

**대응**
{다음에 이 상황을 만나면 무엇을 하는가}

**출처**
{커밋 해시 / 리뷰 보고서 경로 / 날짜}
```

`type` 구분:

| type | 무엇 |
|---|---|
| `pitfall` | 밟으면 버그가 되는 함정 |
| `convention` | 이 저장소가 따르는 관례 (코드를 읽어도 이유를 알 수 없는 것만) |
| `environment` | 도구·런타임·하네스 실행 환경의 제약 |
| `process` | 워크플로 자체에서 배운 것 (묶음 크기, 순서, 승인 지점) |

## 일반화해서 쓴다

**나쁨:** "Task 5에서 `structuredText` 재사용 분기를 놓쳤다."
**좋음:** "두 컬럼이 하나의 상태를 나타낼 때, 재처리를 위해 상태 컬럼만 되돌리면 재사용 분기가 남아 있는 옛 내용을 유효한 것으로 보고 완료로 수렴시킨다."

좁은 규칙은 다음 상황에 맞지 않아 읽히고도 적용되지 않는다. **증상을 구조로 바꿔서 쓴다.**

동시에 **왜를 반드시 남긴다.** 지시만 있으면 다음 에이전트가 엣지 케이스에서 잘못 적용한다. 그 규칙이 없었을 때 실제로 무슨 일이 일어났는지가 판단 기준이 된다.

## 승급 — 언제 하네스 자체를 고치는가

| 신호 | 조치 | 대상 |
|---|---|---|
| 같은 성질의 지적 **1회** | 학습 파일만 기록 | `.claude/learnings/` |
| 같은 성질의 지적 **2회 이상** (이번 실행 내 또는 기존 학습과 합산) | 규칙으로 승급 | 해당 `SKILL.md` 본문 또는 `references/known-pitfalls.md` |
| 특정 에이전트가 반복적으로 같은 실수 | 작업 원칙 수정 | `.claude/agents/{name}.md` |
| 워크플로 순서·단계 자체의 문제 | 오케스트레이션 수정 | `.claude/skills/tb-harness/SKILL.md` |
| 스킬이 트리거되지 않아 사람이 우회함 | description 확장 | 해당 스킬 frontmatter |
| 사용자가 같은 피드백을 2회 이상 | 해당 위치에 규칙으로 명문화 | 피드백 성격에 따라 |

**2회 규칙을 지킨다.** 스킬 본문은 매번 컨텍스트에 로드되므로, 1회성 지적을 규칙으로 승급하면 스킬이 부풀고 부푼 스킬은 읽히지 않는다.

승급했으면 학습 파일의 `promoted_to`에 대상 경로를 적고 `occurrences`를 갱신한다.

## 승급할 때는 늘리지 말고 바꾼다

- 기존 규칙과 겹치면 **새 항목 추가 대신 기존 항목을 정확하게 고친다.**
- `SKILL.md` 본문 **500줄 상한**을 지킨다. 넘치면 `references/`로 옮기고 본문에 "언제 이 파일을 읽으라"는 포인터를 남긴다.
- `references/known-pitfalls.md`에 추가할 때는 기존 분류(A~F) 안에 넣는다. 새 분류를 만들기 전에 기존 분류로 설명되는지 확인한다.

## 틀린 학습은 지운다

기존 학습 중 이번 실행이 **반증한 것**이 있으면 파일을 삭제하거나 정정한다. 틀린 학습은 없는 학습보다 나쁘다 — 다음 에이전트가 그것을 근거로 잘못 판단한다.

정기 점검 항목:
- 참조하는 파일·함수·플래그가 아직 존재하는가
- 설계 변경으로 무효가 된 함정인가
- 두 학습이 같은 말을 하고 있는가 (병합)

## CLAUDE.md 변경 이력

**하네스를 고쳤으면 반드시 기록한다.**

```markdown
| {YYYY-MM-DD} | {변경 내용} | {대상 파일} | {사유} |
```

이력이 없으면 다음 compound가 근거를 모른 채 같은 변경을 되돌린다.

학습 파일만 추가한 경우는 이력에 적지 않는다 — 하네스 변경이 아니다.

## 사람에게 넘기는 것

다음은 직접 고치지 말고 **제안으로 반환**한다:
- 정책·취향에 걸리는 변경 (커밋 단위 정책, 언어 규약, 리뷰 심각도 기준)
- 워크플로 단계를 추가·삭제하는 변경
- 서로 반대되는 두 학습 — 어느 쪽이 맞는지 판단이 필요할 때

## 아무것도 없을 때

**"이번 실행에서 새로 배운 것 없음"은 정당한 결과다.** 억지 학습은 다음 실행의 컨텍스트를 오염시킨다. 매끄럽게 끝난 실행이 남길 것이 없는 건 정상이다.

## 입력

- `.claude/_workspace/{run-id}/journal.md` — 실행 저널
- `.claude/_workspace/{run-id}/findings-*.md` — 통합 지적과 처리 결과(수정/반박/보류)
- `.claude/learnings/` 전체 — **반복 여부 판정에 필수**
- 계획·spec 문서 — 계획 이탈의 맥락
- `git log` — 이번 실행이 만든 커밋

저널이 없으면(하네스를 거치지 않은 실행) git 이력과 리뷰 보고서만으로 진행하고 그 사실을 보고한다.
