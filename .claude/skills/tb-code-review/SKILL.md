# 코드 리뷰 규약

리뷰의 목적은 **결함을 찾는 것**이지 코드에 의견을 남기는 것이 아니다. 지적 하나가 구현자의 시간을 태우므로, 태울 값어치가 있는 것만 낸다.

리뷰를 시작하기 전에 `references/known-pitfalls.md`를 읽는다. 이 저장소에서 **실제로 발생해 커밋으로 수정된** 결함 유형이며, 같은 유형이 계속 재발한다.

## 검증 게이트 — 이걸 통과 못 한 지적은 버린다

**모든 지적은 구체적 실패 시나리오를 가져야 한다.**

```
입력/상태: {구체적인 값 또는 상황}
       ↓
잘못된 결과: {실제로 무슨 일이 일어나는가}
```

시나리오를 만들 수 없다면 그것은 결함이 아니라 인상이다. 인상은 적지 않는다.

**게이트를 강화하는 방법 — 실제로 돌려본다:**

| 축 | 증명 방법 |
|---|---|
| 정확성 | 가설을 검증하는 테스트를 임시로 작성해 돌리고, 실패 출력을 지적에 첨부 |
| 계약 | 경계 **양쪽 파일을 나란히 인용**. 한쪽만 인용한 지적은 교차 비교를 안 한 것 |
| 테스트 품질 | 구현을 임시로 망가뜨려 돌리고 **여전히 통과함**을 확인 |

임시로 만든 테스트·수정은 **반드시 원복하고 커밋하지 않는다.**

## 심각도

| 등급 | 기준 | 처리 |
|---|---|---|
| **Critical** | 데이터 손상·유실, 소멸성 자원 낭비, 정상 데이터의 영구 제외, 보안 | 즉시 수정. 다음 묶음으로 진행 금지 |
| **Major** | 특정 입력에서 잘못된 결과, 복구 불가능한 상태, 테스트가 검증하지 못하는 핵심 경로 | 이번 묶음 안에서 수정 |
| **Minor** | 좁은 조건에서만 드러남, 운영자 대면 문구, 방어 부족 | 묶어서 나중에 처리 가능 |
| **Note** | 다음 설계 때 고려할 것 | 수정 요구 아님. compound로 넘김 |

**전부 Critical이면 아무것도 Critical이 아니다.** 등급을 정직하게 매기는 것이 리뷰 신뢰의 전부다.

## 지적 포맷

````markdown
### [{심각도}] {한 줄 제목}

**위치:** `{파일}:{줄}` {필요하면 두 번째 위치}

**실패 시나리오**
{입력/상태} → {잘못된 결과}

**근거**
```{lang}
{문제가 되는 코드}
```
{왜 이게 틀렸는지. 어떤 가정이 깨졌는지.}

**증명**   ← 실행으로 확인했을 때만
```
{돌린 명령과 출력}
```

**제안**
{어떻게 고칠지. 코드로 쓸 수 있으면 코드로.}
````

## 보지 않는 것

- 스타일·네이밍·포맷 (린터와 prettier의 일이다)
- 취향에 가까운 구조 선호 ("이건 클래스로 빼는 게…")
- 이미 상위·하위 계층에서 막고 있는 방어의 중복 요구
- 계획이 명시적으로 범위 밖이라고 선언한 것
- 성능 — **측정 없이는 지적하지 않는다.** 이 프로젝트는 속도가 요구사항이 아니다

## 리뷰 전에 반드시 하는 일

1. **spec과 계획을 실제로 읽는다.** 기억·추정으로 이탈을 판정하지 않는다.
2. **diff만 보지 않는다.** 변경된 함수의 **호출자 전부**를 읽는다. 결함은 대개 변경된 줄이 아니라 그 변경이 깨뜨린 가정에 있다.
3. **`.claude/learnings/`를 읽는다.** 과거에 잡힌 유형이 이번에도 있는지 먼저 확인한다.
4. **테스트와 타입 검사를 직접 돌린다.** 통과한다는 구현자의 주장을 그대로 받지 않는다.

## 리뷰 대상 범위

오케스트레이터가 지정한 **커밋 범위**만 본다. 대개 `git log --oneline {base}..HEAD` 와 `git diff {base}..HEAD`.

범위 밖에서 결함을 발견하면 지적하되 **`[범위 밖]` 표시**를 붙인다. 이번 수정 대상이 아니라 compound 단계의 입력이다.

## 3축 병합 — 오케스트레이터가 한다

리뷰어 셋은 서로의 결과를 보지 않는다. 겹치는 지적이 나오는 것은 정상이며, **다른 축의 영역이라고 생각해 빠뜨리는 것보다 낫다.**

병합 규칙:
- 같은 위치·같은 원인 → 하나로 합치고, **가장 높은 심각도**를 채택
- 같은 뿌리의 다른 증상(정확성 결함 + 그것을 못 잡는 테스트 공백) → **묶어서 하나의 수정 태스크**로 만든다. 따로 고치면 수정과 회귀 테스트가 서로 다른 커밋으로 흩어진다
- 서로 반대되는 지적 → 삭제하지 말고 **양쪽을 병기**해 사용자 판단으로 올린다

## 결함이 없을 때

**"지적 없음"은 정당한 결과다.** 억지 지적 3건보다 정직한 0건이 낫다. 무엇을 봤는지(파일 목록·실행한 명령)를 보고서에 남겨 "안 봐서 없는 것"과 구분되게 한다.

## 재검증 모드

수정 후 재호출되면:

1. 이전 보고서의 지적별로 **`해소 / 미해소 / 부분 해소`**를 판정한다.
2. **수정에 회귀 테스트가 붙었는지 확인한다.** 없으면 미해소다 — 수정만 하고 테스트를 남기지 않으면 같은 버그가 돌아온다.
3. 구현자의 **반박을 검토한다.** 반박이 옳으면 지적을 철회하고 그 사실을 명시한다. 리뷰어도 틀린다.
4. 새 지적은 **별도 절로 분리**한다. 재검증이 새 결함 사냥으로 번지면 수렴하지 않는다.
