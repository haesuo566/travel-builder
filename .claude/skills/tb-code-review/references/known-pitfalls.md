# 이 저장소에서 실제로 발생한 함정

git 이력과 설계 문서에서 추출한, **커밋으로 수정된 적이 있는** 결함 유형이다. 같은 유형이 반복 재발했으므로 리뷰 때 이 목록부터 대조한다.

새 유형이 2회 이상 반복되면 `compounder`가 여기에 추가한다.

## A. 실패 분류 — 책임을 잘못된 대상에게 청구

이 저장소에서 **가장 자주 재발한** 유형이다. 판단 기준은 하나: **이 실패의 책임이 데이터에 있는가, 호출자 사정에 있는가, 우리 저장소에 있는가.**

### A-1. 쿼터 소진을 데이터 결함으로 기록

**증상:** 외부 API가 rate limit(429)·일일 한도로 실패했는데 그 항목의 `attempt_count`를 올린다.
**결과:** 매일 한도가 끝나는 지점의 항목이 하루 한 번씩 실패를 쌓아, 사흘이면 **멀쩡한 데이터가 `failed`로 영구 제외**된다.
**점검:** 429·한도초과 분기에서 `mark*Failure`를 호출하지 않는지. 백오프 재시도 후에도 실패하면 **상태를 그대로 두고** 다음 실행에 맡기는지.

### A-2. 시스템 장애가 개별 항목 오류로 위장

**증상:** API 키 만료·네트워크 단절은 429도 아니고 정상도 아니라서 "기타 오류" 분기로 들어온다.
**결과:** 차단기가 없으면 claim한 **전량**에 실패가 기록된다.
**점검:** 연속 실패 차단기가 있는지. **그 차단기가 모든 진입 경로에서 트립되는지**(→ C-1).

### A-3. DB 쓰기 실패를 외부 호출 실패로 분류

**증상:** `try` 블록이 외부 호출과 DB 쓰기를 함께 감싼다.
**결과:** 외부 호출은 성공했는데 `mark*Done`이 실패한 경우가 "외부 오류" 분기로 흘러, **이미 태운 쿼터를 버리면서 멀쩡한 항목의 attempt를 올린다.**
**점검:** `try`가 외부 호출만 감싸는지. DB 쓰기 실패는 삼키지 않고 **전파**하는지.

### A-4. 복구 가능한 실패가 소멸성 자원을 태운다

**증상:** 하위 단계(임베딩·구조화)의 실패가 예외로 전파돼 상위 루프를 중단시킨다.
**결과:** 오늘 쓰지 않으면 사라지는 API 예산이 **복구 가능한 실패 때문에** 낭비된다.
**점검:** 자원 등급이 다른 두 작업을 한 루프에 넣었을 때, **희소한 쪽이 흔한 쪽의 실패에 인질로 잡히지 않는지.** 하위 단계가 자기 실패를 스스로 삼키고 정상 반환하는지.

### A-5. 우리 설정이 만든 404를 외부 장애로 청구

**증상:** 상태 코드 분류기가 400·413·422만 특별 처리하고 나머지 비-2xx를 `upstream`으로 떨어뜨린다. 404가 그 나머지에 섞인다.
**결과:** 모델명 오타·엔드포인트 경로 오설정·컬렉션명 오타가 전부 **502 "외부 서비스에서 오류가 발생했습니다."** 외부 서비스는 멀쩡하고 틀린 것은 우리 `.env`인데, 응답과 로그를 받은 사람은 외부 장애를 조사한다.
**점검:** 경로·모델명·컬렉션명은 요청 내용과 무관하게 고정이므로 404의 책임이 설정에 있는지 — 그러면 `not-found`다. **서비스가 달라도 같은 종류의 오설정은 같은 kind인지 대조한다**(한 서비스만 예외면 지적이다). `'분류되지 않은 비-2xx는 upstream이다'` 류의 테스트가 404를 품어 **잘못된 결정을 못 박고 있지 않은지.**
**부재 선언 점검:** spec이 "이 서비스에는 `auth`·`quota`·`not-found`가 없다"처럼 여러 kind를 한 줄로 부정했으면 **부정한 항목 수만큼 근거가 있는지 센다.** 근거가 하나뿐이면 판단된 게 아니라 빠진 것이고, 에러 처리 표에 그 행 자체가 없으면 확정 신호다.

## B. 상태·멱등성

### B-1. 하나의 상태를 두 컬럼이 나눠 가짐

**증상:** `structured_text`(내용)와 `structure_status`(상태)가 같은 사실을 나타내는데, 재처리 시 `status`만 되돌린다.
**결과:** 재사용 분기가 남아 있는 **옛 내용을 유효한 것으로 보고 `done`으로 수렴**시킨다. 재생성이 영원히 일어나지 않는다.
**점검:** 재사용·캐시 분기가 **단일 진실 원천 하나**만 보는지. 되돌리는 SQL이 두 컬럼을 함께 되돌리는지. 문서에 그 SQL이 명세돼 있는지.

### B-2. 재실행이 중복을 쌓음

**증상:** 파생 저장소(벡터 DB 등)의 id가 랜덤이다.
**결과:** upsert는 성공했는데 직후 상태 커밋이 실패하면, 다음 실행이 **유령 레코드**를 하나 더 만든다.
**점검:** id가 원본 키에서 **결정론적으로** 유도되는지. 파싱 실패 시 스킵하고 기록하는지.

### B-3. 커밋 경계가 비용을 보호하지 않음

**증상:** 비용을 지불한 작업(외부 API 호출)과 이후 단계가 한 트랜잭션에 묶여 있다.
**결과:** 뒷단 실패가 이미 소비한 쿼터를 날린다.
**점검:** **비용 지불 직후 즉시 커밋**하는지. 그 아래의 모든 실패가 복구 가능한지.

## C. 차단기·상한

### C-1. 차단기가 특정 경로에서 트립되지 않음

**증상:** 차단기 카운터를 올리는 코드가 한 진입 경로에만 있다.
**결과:** 다른 경로(인라인 vs 백로그)로 들어오면 차단기가 **절대 트립되지 않아** 손상이 무한히 번진다.
**점검:** 같은 로직에 진입 경로가 둘 이상이면, 카운터 증가·차단 판정이 **양쪽 모두**에서 일어나는지. 두 경로가 같은 함수를 재사용하게 돼 있는지.

### C-2. 상한 판정 off-by-one

**증상:** `attempt_count + 1 >= max` vs `attempt_count >= max`.
**결과:** 재시도가 한 번 적거나 많다. 조용해서 오래 안 잡힌다.
**점검:** 증가와 전이가 **단일 UPDATE의 CASE**로 원자적으로 처리되는지. 테스트가 경계값(`max-1`, `max`)을 모두 덮는지.

## D. 스키마·DDL

### D-1. `CREATE TABLE IF NOT EXISTS`가 기존 테이블에 no-op

**증상:** 테이블 생성 함수에 컬럼을 추가했다.
**결과:** 테이블이 **이미 존재하므로 구문 전체가 no-op**이 되고 신규 컬럼이 절대 생기지 않는다. 로컬 신규 DB에서는 통과하고 운영에서만 깨진다.
**점검:** `CREATE TABLE` 뒤에 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`가 따라오는지. 테스트가 발행 SQL에서 `ALTER TABLE`을 확인하는지.

### D-2. 부재(404)와 장애를 구분하지 않음

**증상:** 조회 실패를 전부 "없음"으로 변환한다.
**결과:** **연결 장애를 "컬렉션 없음"으로 오분류**해, 기존 컬렉션 위에 다른 설정으로 재생성을 시도한다.
**점검:** 404만 `null`로 바꾸고 나머지는 전파하는지. 파괴적 작업(삭제·재생성)을 자동으로 하지 않는지 — 그건 사람이 결정할 일이다.

## E. 테스트

### E-1. 대칭 케이스 누락

**증상:** `A일 때 호출됨`은 있는데 `A가 아닐 때 호출 안 됨`이 없다. 성공만 있고 실패가 없다.
**결과:** 조건 분기가 통째로 사라져도 테스트가 통과한다.
**점검:** 분기마다 양쪽 방향이 다 있는지. spec 에러 처리 표의 **행 수와 테스트 수를 대조**한다. **형제 파일 간 대칭도 본다** — 한 클라이언트가 "env 없으면 부팅 실패"를 고정했는데 옆 클라이언트에 그 케이스가 없으면 누락이다. 상위(모듈) 테스트는 대체재가 아니다: env를 전부 비우면 **먼저 던지는 프로바이더 하나가 단정을 만족시켜** 나머지가 안 던져도 초록불이다.

### E-2. assertion이 구현을 복사

**증상:** SQL 문자열이나 출력 포맷을 그대로 복사해 비교한다.
**결과:** 구현이 틀리면 테스트도 함께 틀린다.
**점검:** assertion이 **의미 있는 부분 조건**(예: `WHERE detail_status = 'done'`을 포함하는가)을 보는지, 전문 일치인지.

### E-3. 수정만 있고 회귀 테스트가 없음

**증상:** 리뷰 지적을 고친 커밋에 테스트 변경이 없다.
**결과:** 같은 버그가 돌아온다. 이 저장소에서 실제로 반복됐다.
**점검:** 수정 커밋마다 그 버그를 **재현하는** 테스트가 붙었는지.

### E-4. 단정이 약함

**증상:** `toBeDefined()`, `toBeTruthy()`로 끝난다.
**결과:** 잘못된 값도 통과한다.
**점검:** 무엇이 나와야 하는지 정확히 단정하는지.

## F. 워크스페이스 경계

타입 시스템이 연결해주지 않는 지점들이다. **한쪽만 고치면 컴파일은 통과하고 런타임에 깨진다.**

### F-1. backend DTO ↔ frontend 소비 shape

**현재 상태:** `backend/src/chat/dto/chat-response.dto.ts`는 주석으로 *"프론트엔드 `frontend/src/lib/mock/scenarios.ts`의 `ScenarioResult`와 같은 모양"*이라고 선언하지만, `frontend/src/lib/api/itinerary.ts`는 여전히 mock을 직접 호출한다. **HTTP로 배선하는 순간 검증되는 계약**이고, 그때까지는 아무도 안 깨진다.
**점검:** DTO를 바꿀 때 `frontend/src/lib/types.ts`와 `src/lib/api/*.ts`를 **함께 연다.** 주석에 적힌 "같은 모양"을 믿지 말고 필드를 하나씩 대조한다.

### F-2. core DDL ↔ backend TypeORM 엔티티

`core/src/lib/*Table.ts`의 DDL과 `backend/src/database/entities/*.entity.ts`가 **같은 테이블**을 가리킨다. 컬럼 추가·타입 변경 시 양쪽을 함께 본다.

### F-3. snake_case ↔ camelCase 사슬

SQL 별칭 → row 인터페이스 필드 → 도메인 객체 프로퍼티. 세 칸 중 하나만 어긋나도 **타입 검사는 통과하고 런타임에 `undefined`가 흐른다.**
**점검:** 매핑 함수의 좌변·우변을 한 줄씩 대조한다. 필드 개수도 센다.

### F-4. 타입은 맞고 의미가 다름

양쪽 다 `string`인데 한쪽은 코드(`"12"`), 다른 쪽은 이름(`"관광지"`). 컴파일은 통과하고 데이터가 틀린다.
**점검:** 경계를 넘는 문자열 필드의 **값 예시**를 양쪽에서 확인한다.

### F-5. env 변수 3중 등록 누락

새 환경변수는 세 곳에 함께 들어가야 한다: `.env.example` · 검증 모듈(`core/src/lib/env.ts` 또는 `backend/src/config/env.validation.ts`) · 사용처.
