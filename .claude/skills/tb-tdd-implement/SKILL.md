# 구현 규약

계획의 태스크를 순서대로, 태스크당 다섯 Step으로 처리한다.

작업 전에 대상 워크스페이스의 명령과 제약을 `references/workspaces.md`에서 확인한다. `core`/`backend`/`frontend`는 테스트 러너·모듈 시스템·타입 검사 방법이 전부 다르다.

## 다섯 Step

```
1. 실패하는 테스트 작성
2. 실패를 눈으로 확인          ← 건너뛰지 않는다
3. 구현
4. 통과 확인 (전체 테스트 + 타입 검사)
5. 커밋
```

### Step 2를 건너뛰지 않는 이유

실패를 확인하지 않으면 나중에 통과했을 때 **구현이 옳아서인지 테스트가 아무것도 검증하지 않아서인지 구분할 수 없다.** 이 저장소에서 실제로 나온 결함 유형이다.

**예상과 다른 이유로 실패하면 그것부터 고친다.** 오타·import 경로·모듈 없음으로 실패하는 상태에서 구현을 시작하면, 테스트가 무엇을 검증하는지 아무도 모르게 된다.

### Step 4는 전체다

방금 쓴 테스트 파일만 돌리지 않는다. 해당 워크스페이스의 **테스트 전체 + 타입 검사**를 통과시킨 뒤 커밋한다. 부분 실행은 회귀를 놓친다.

## 계획을 벗어날 때

다음 상황에서는 **임의로 고쳐 진행하지 않고 멈추고 보고한다.**

- 계획의 코드 블록이 현재 코드와 맞지 않는다
- 계획대로 하면 기존 테스트가 깨진다
- 계획이 놓친 케이스를 발견했다
- 계획에 없는 결정이 필요해졌다

계획과 코드가 벌어지면 리뷰어가 이탈을 판정할 기준을 잃는다. **이탈은 결함이 아니라 정보다** — 보고하면 계획이 갱신되고, 숨기면 리뷰가 잘못된 기준으로 판정한다.

### 계획의 코드 블록을 그대로 믿지 않는다

블록은 **계획 작성 시점의 스냅샷**이다. 그 뒤에 spec이 정정됐거나 앞 태스크가 같은 파일을 건드렸을 수 있다.

- **`교체 후 전문`이라도 덮기 전에 현재 파일과 대조한다.** 줄 수·테스트 개수가 다르면 계획이 낡은 것이다. 덮으면 앞 태스크가 추가한 커버리지가 **회귀하는데 테스트는 초록불이다** — 실제로 테스트 3건이 그렇게 사라질 뻔했다.
- 블록 위의 `> **[갱신 …]**` blockquote를 먼저 읽는다. 아래 코드보다 그쪽이 최신이다.
- 계획 블록과 커밋된 코드가 다르면 **커밋된 코드가 기준**이다. 차이를 이탈로 보고한다.

## 금지 사항

| 하지 말 것 | 이유 |
|---|---|
| 기존 테스트를 고쳐서 통과시키기 | 회귀인지 의도된 변경인지 판단하지 않고 증거를 지우는 행위 |
| `any` · `@ts-ignore` · `as unknown as`로 타입 오류 덮기 | 타입이 안 맞으면 설계가 안 맞는 것이다 |
| 여러 태스크를 한 커밋에 묶기 | 되돌릴 단위가 사라진다 |
| 이번 태스크 밖의 파일 손보기 | 리뷰 범위가 번지고 diff가 읽히지 않는다. 발견 사항은 보고로 넘긴다 |
| 테스트에서 실제 네트워크·DB 호출 | 이 저장소의 테스트는 전부 모킹이다 |
| 3회 시도해도 안 되는 것을 억지로 통과시키기 | 중단하고 막힌 지점을 보고한다 |

## 커밋

```
{type}({scope}): {한국어 제목}

{왜 이렇게 했는지 2~4줄}
```

- `type`: `feat` `fix` `refactor` `test` `docs` `chore`
- `scope`: `core` `backend` `frontend` (여러 워크스페이스면 생략)
- **본문은 왜만 쓴다.** 무엇을 했는지는 diff가 말한다.

좋은 예:
```
feat(core): tour_contents에 구조화·임베딩 스테이지 컬럼 추가

CREATE TABLE IF NOT EXISTS는 기존 테이블에 no-op이라 컬럼이 생기지
않는다. ALTER TABLE ... ADD COLUMN IF NOT EXISTS로 신규 생성과 기존
갱신을 한 곳에서 처리한다.
```

커밋 후 계획 문서의 해당 체크박스를 `- [x]`로 바꾼다.

## 코드 규약

- **주석·로그·에러 메시지는 한국어.** 기존 코드 전체가 그렇다.
- **주석은 왜를 쓴다.** 무엇을 하는지는 코드가 말한다. 비직관적인 선택에만 붙인다.
- 주변 코드의 네이밍·구조·주석 밀도를 따른다. 새 스타일을 들여오지 않는다.
- 에러 메시지에 **판단 재료**를 담는다. `"차원 불일치"`가 아니라 `"컬렉션 X의 차원 768, 감지된 차원 1024"`.

## 리뷰 지적 수정 모드

리뷰 지적 목록을 받아 재호출됐을 때:

1. **지적 하나당 커밋 하나.** 제목은 `fix({scope}): {지적 요지}`.
2. **지적을 재현하는 테스트를 먼저 추가한다.** 수정만 하고 테스트를 남기지 않으면 같은 버그가 돌아온다 — 회귀 테스트 없는 수정은 리뷰어가 미해소로 판정한다.
3. **동의하지 않는 지적은 고치지 말고 반박 근거와 함께 반환한다.** 리뷰어도 틀린다. 납득하지 못한 채 고친 코드가 가장 위험하다.
4. 지적별로 `수정함 / 반박 / 범위 밖으로 보류` 중 하나를 **빠짐없이** 명시한다. 조용히 빠뜨리지 않는다.

여러 지적을 한 커밋에 묶으면 어느 수정이 어느 지적에 대응하는지 재검증이 추적할 수 없다.

## 보고 형식

반환 메시지에 담을 것:

```
커밋: {해시} {제목}   ← 태스크별로 한 줄씩
계획 이탈: {없음 | 항목별 서술}
테스트: {명령} → {결과}
타입 검사: {명령} → {결과}
발견 사항: {다음 단계로 넘길 것 — 범위 밖이라 손대지 않은 것들}
```
